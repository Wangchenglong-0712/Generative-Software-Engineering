论述E1 §5.1 心智模型 / §5.4 · 10 分

课堂上反复强调一句话：「预测下一个 token」是训练接口，不是能力上限；而使用者最有用的心智模型是 「它不是答案数据库，而是一个由 context 条件化的模拟器——我们真正『编程』的是 context」。

请围绕这两句话展开论述：

  • 为什么一个只做 next-token 预测的模型，能够承载草稿、算法和推理？请解释「自回归把静态分布展开成计算过程」。
  • 为什么流畅 ≠ 正确？「流畅」到底证明了什么、又没有证明什么？
  • 既然我们编程的对象是 context，那么在使用 Agent 时，应当建立哪些具体的检验习惯？（请至少给出三条可执行的做法）
作答要点
  • 训练接口 ≠ 能力上限：要同时预测代码、证明、对话和故事，模型被迫压缩语言背后的世界规律；目标函数简单，不代表由此习得的表示简单。
  • 自回归 = 把分布展开成过程：每个输出都会被写回 context，于是「先写中间结果 → 基于它继续 → 发现矛盾再修正」成为可能；足够长的 token 序列因此可以承载草稿、搜索和算法轨迹。
  • 流畅只说明「在这个上下文里像一个答案」：它是分布内似然的证据，不是正确性的证据；尤其在缺少可观测反馈时，模型会用更长的文字把错误说得更完整。
  • 检验习惯：① 要求给出可回查的出处/中间产物，而不只是结论；② 让结论落到可执行的验证（脚本、oracle、真实解码器）上；③ 给 context 注入反例与约束，做对抗式提问；④ 对长任务拆步并要求每步的证据，而不是等终局再验收。

论述E2 §11.1–§11.3 古法编程死了 / · 10 分

第 11 节的标题是「古法编程死了，软件工程还没死」。请论述：

  • 这条分界线究竟划在哪里？请用「边界清楚、上下文装得下、结果能低成本验收」三个条件说明什么样的任务已经进入机器的领地。
  • 用「Computer 原本是一种职业」的历史类比，说明为什么历史不奖励把旧动作做得更快的人。
  • 课程说人的稀缺性是方向 × 验证 × 责任。请分别解释这三项，并论证为什么它们相乘而不是相加。
  • 「禁止古法编程」是否等于「禁止理解程序」？请给出你的判断与理由。
作答要点
  • 分界线：边界清楚（可完整描述）、上下文装得下（信息可进入 context）、结果能低成本验收（有便宜的 oracle）——三条同时满足，任务就落入机器领地。缺任何一条，人的判断仍然必要。
  • 历史类比：电子计算机出现后，优秀的 human computers 转向编程与研究；被淘汰的不是「计算能力」，而是「以手工方式执行确定性流程」这一角色。
  • 相乘而非相加：三者互为前提——没有方向的验证是盲测，没有验证的方向是许愿，没有责任的二者都不必收敛。任一项趋近 0，整个乘积趋近 0，无法用另一项的强度补偿。
  • 禁止古法编程 ≠ 禁止理解：禁止的是「把亲手敲出每一行代码当作学习成果」；正确的顺序是先让 Agent 生产，把人的注意力押在定义问题、设计验收、解释失败上。理解的对象从「语法」上移到「结构与约束」。
  • 可加分：用本学期的自我追问收尾——我发现了什么值得解决的问题？我怎样把模糊愿望变成可检验的目标？失败时我凭什么知道该换路？

论述E3 §9.2–§9.4 qrgen 暴毙 · 10 分

qrgen 的需求只有短短几行，两份 2 MB 的 Excel 也都「跑出来了」。讲义却把它们的失败归结为一句话： 「AI slop 的本质不是文件大，而是改动没有局部性」。

  • 为什么「需求很短」不等于「规格空间很小」？请从 qrgen 的需求里找出至少三处被隐藏的规格分支。
  • 请论证：为什么说硬编码是把 ∀x 的程序问题，偷偷换成了「让这个 x₀ 通过」？
  • 什么是「改动的局部性」？为什么它比文件大小、比代码行数更适合作为可维护性的判据？
  • 「少量 prompt 换一个架构」为什么能成功？请说明从「生成一个能跑的文件」到「设计一个可复用的计算结构」之间的差别。
作答要点
  • 隐藏的规格分支：字符串编码（UTF-8？字节序？）、每帧容量与分片策略、输入变化时公式/工作表是否重建、「F9 刷新」与「1 秒一帧」如何配合、以及最关键的——验收是「文件能打开」还是「每帧可被真实解码器读取、拼接后还原原文」。
  • 硬编码之罪：需求是 ∀s: Base64⁻¹(concat(scan(frames(s)))) = bytes(s)；硬编码版本只保证某一个 s₀ 成立。它把全称量化偷换成存在量化，可以演示成功，却没有实现需求。
  • 局部性：一个需求变化应当只迫使系统的一小块改变。2 MB 只是症状——真正致命的是「改一个需求 → 整张表重新生成」，因为结构与数据耦合，不存在可复用的公式模板。
  • 换架构：从「生成产物」切换到「设计计算结构」——公式可复用、工作表不随文本长度膨胀；判断标准是 O(1) vs O(n)：公式模板与结构相对输入长度保持常数，只有数据、计算量和帧数线性增长。
  • 可加分：指出 GLM-5.3 第一次用了 25 分钟 CoT 仍超 32K 上限、DeepSeek V4 Pro 最终交出硬编码版并自认 “fundamental design flaw”——说明「再多想一会儿」不能替代架构切换。

论述E4 §9.5–§9.6 / §9.9 Intent·Spec·Impl · 10 分

本课主线是三层缺口：Intent Space → Spec Space → Impl Space。讲义给出两条断言： ① Impl ⊨ Spec 并不推出「满足 Intent」；② spec 不是真相，只是对 intent 的一次有损观测。

  • 请解释三层各自的含义，并说明从 Intent 到 Spec、从 Spec 到 Impl 分别需要什么判断。
  • 为什么「能通过测试」不等于「满足真实意图」？请联系「测试和 reward 看见的常常只是末端 proxy」展开。
  • 这一论断对强化学习（如 GRPO）的 reward 设计意味着什么？为什么 long-horizon 的 reward 信号天然很弱？
  • 模型靠「猜」来补 gap。既然猜不可避免，目标应如何调整？请结合决策不等式 P(猜错) × C(返工) > C(澄清) 说明。
作答要点
  • 三层：Intent 是你真正想达成的目标（提出者自己往往也不 100% 确定）；Spec 是具体化后能描述行为与约束的规格；Impl 是程序实际执行的计算——计算机只接受 100% 无歧义的指令，不能留一句「到时候看着办」。
  • 判断的位置：Intent → Spec 需要产品判断，Spec → Impl 需要设计与实现判断；同一个意图允许许多规格，同一个规格允许许多实现。
  • 测试 ≠ 意图：测试只能证明 Impl ⊨ Spec；而 spec 本身已是对 intent 的有损观测。于是「测试全绿」只说明末端 proxy 达标，不能替人决定「这是不是我想要的」。
  • 对 RL 的含义：reward 是 spec 的又一次有损压缩，long-horizon 任务的反馈稀疏且延迟，信号很弱；人在项目失败后会「三观尽毁」再重生（方法论重塑），模型没有等价机制。
  • 猜不可能消灭：总不能每选一种颜色、每命名一个变量都问用户；目标是让猜测显式、可逆、可验证。低影响决策先猜后验；高影响、难回滚的决策先停下来问——即当 P(猜错)×C(返工) > C(澄清) 时提问，否则先做最小实验。

论述E5 §10 成本结构变了 · 10 分

第 10 节给出一道乘法题：1000× 产量 × 1% 垃圾率 = 10× 旧时代全部产量的垃圾， 结论是「瓶颈不再是生产，而是验证」。

  • 请论证：「错误率很小」与「维护负担很小」为什么不是一回事？
  • 为什么「生成可以并行，逐行 review 却不能」？这条不对称性会把工程组织推向什么形态？
  • 课程由此提出的新工程任务是「让 spec、oracle、门控、观测和抽样本身也能扩展」。请解释这句话，并说明「让判断也具备规模效应」具体指什么。
  • 如果 AI 连「品味」也学会，人的稀缺性继续向上游迁移。请讨论：那时真正困难的问题会变成什么？（提示：为何做、为谁做、后果由谁承担）
作答要点
  • 错误率 vs 维护负担：错误率是按件计的比率，维护负担是按量计的绝对数；产量放大 1000× 后，即便 1% 也是旧时代全部产量的 10 倍。99% 正确，在规模面前仍然是灾难。
  • 不对称性：生成是并行的（1000 个 Agent 同时写），而人的 review 是串行、受注意力约束的；于是组织形态从「人写 + 人查」转向「机器写 + 机器门控 + 人抽样」，人只驻守最窄的高风险接口。
  • 让判断规模化：把验收本身工程化——spec 可执行、oracle 独立于实现、CI 作为门控、观测与日志可回查、抽样降低人的审查量；目标是人的注意力花在最值得判断的地方。
  • 品味之后：能力可以迁移，正当性与问责不会自动迁移；问题从「怎么做」转向「为何做、为谁做、后果由谁承担」。时代红利则是每个人都有机会去解决以前连开始都不敢想的 long-horizon 问题。

论述E6 §8.3–§8.4 / §11.2 · 10 分

课堂 Quiz：一台「文件只进不出」的机器，怎么把文件偷出来？解法是—— Rx 用鼠标（鼠标也是输入线路），Tx 用二维码（Excel 是可编程显示设备），在一条 Raw Socket 上自建协议栈。

  • 请说明这个解法的关键思维动作是什么？讲义称之为「重解释」，请给出你的定义。
  • 从这个例子出发，论证「Everything Is Code」：为什么视频、论文、零件只是不同后端？
  • 把「重解释」迁移到你自己身上：课堂上还有一句话是「为什么要招你，而不是买一个 $200 的 Claude Max？」 请写一段 30 秒的回答，并批判性地讨论其中「可以坐牢」这个说法——在什么条件下，责任才不是 moral crumple zone（道德缓冲垫）？
作答要点
  • 重解释：不要只按应用程序的名字想象它的用途，要看它实际上提供了什么输入、计算和输出能力。安全边界限制了「文件」，却没有限制信息——只要像素仍可被观察，出口容量就不为零。

  • 30 秒模板：我能找到值得解决的问题，把未知拆成便宜的实验，用证据让坏方向及时停下，并对长期结果负责。
  • 对「坐牢」的批判：「可以坐牢」只点出了责任；责任必须与最终决策权、情境判断与停止权绑定。没有这些权力却只负责背锅的人，只是自动化系统的 moral crumple zone。

解答S1 §5.3 算术很重要 · 8 分

（1）若 Agent 每一步的成功率为 95%，且各步独立，连续 50 步全部正确的概率是多少？ （2）若希望一个 100 步任务的整体成功率不低于 90%，单步成功率至少应达到多少？ （3）由此说明：为什么在长任务里，「好一点」可能意味着从不可用到能用？

参考答案
  1. 0.95⁵⁰ ≈ 0.0769，即约 7.7%——看似很高的单步成功率，50 步后几乎必败。
  2. 设单步成功率为 p，要求 p¹⁰⁰ ≥ 0.9，则 p ≥ 0.9^(1/100) ≈ 0.99895， 即单步成功率需达到约 99.9%。20 步时 0.95²⁰ ≈ 35.9%，可见步数比单步质量更致命。
  3. 因为整体成功率是单步成功率的指数函数：步数越长，微小的单步差异被放大成可用性上的质变。 所以提升单步可靠性、缩短反馈回路（少走冤枉路）、以及把长任务拆成可独立验收的阶段，都比「让模型再多想一会儿」更有效。 这也解释了 test-time scaling 不是免费的：没有有效反馈的「多想一会儿」，只是把错误说得更长。

解答S2 §9.1 乘积效应 · 8 分

（1）一个产品有 10 个环节，每个环节各有 90% 可靠，整体成功率是多少？ （2）若要把整体成功率提升到 80%，在其他条件不变的前提下，每个环节至少需要达到多少可靠性？ （3）请用这个结果说明：为什么「AI 提高单点产能，不会自动消除接口与协作风险」？

参考答案
  1. 0.9¹⁰ ≈ 0.3487，即约 35%。
  2. 设每环节可靠性为 r，要求 r¹⁰ ≥ 0.8，则 r ≥ 0.8^(1/10) ≈ 0.9779， 即每环节需达到约 97.8%——从 90% 提到 97.8%，远比「把某一环节做到 99.9%」更艰难，因为必须同时提升。
  3. 整体成功率是各环节可靠性的乘积：AI 主要放大的是单点产能（把某个环节写得更快更多）， 而接口、状态所有权、例外处理这些跨环节的耦合并不随单点产能改善；只要任一环节趋弱，乘积就坍塌。 因此工程的重心要从「让每个部分更强」转向「让耦合更少、让错误炸得不远、回退得便宜」——这正是拆解 / 验证 / 迭代这条反馈控制环的意义。

解答S3 §9.11 如何安排 qrgen 的开发 · 8 分

请按「风险退休」的顺序安排 qrgen 的开发，而不是按最终需求堆功能。要求写出： （1）需要先冻结的 invariants；（2）Stage 0–4 各阶段做什么； （3）每一阶段留下的回归门是什么。

参考答案

（1）冻结 invariants：Excel ≤ 2019 公式兼容；Base64 可重组；每一帧可被真实解码器还原；工作表不随输入长度膨胀。

阶段做什么回归门（可执行）
Stage 0先写独立于实现的 oracle随机用例 + 边界用例 + golden cases 全部通过；oracle 不依赖被测实现
Stage 1固定短字符串 → 单帧 QR该帧被真实解码器还原为原文（验证最核心的计算）
Stage 2任意输入 → Base64 与分片正确仍只选一帧；分片拼接后 Base64⁻¹ 等于原始字节
Stage 3多帧顺序、循环、拼接帧序与完整性自动可验证（帧号 + 校验和）
Stage 4最后加入 F9/定时、兼容性、性能兼容性矩阵与耗时阈值；工作表体积对输入长度保持 O(1)

要点：每一阶段只消除一种具体的不确定性，并留下可执行的回归门；不是等整个文件写完再看能不能用。 顺序原则是让最难回滚、最容易推翻架构的风险最先退休。

解答S4 §9.4 架构检查题 · 8 分

架构检查题：输入从 1 KB 变成 10 KB 时，究竟有哪些东西必须增长？

  • 请分别列出应当保持 O(1) 的部分，与按 O(n) 增长的部分。
  • 为什么「工作表不随输入长度膨胀」是一个好的可维护性判据？
  • 请给出一条你能在这周就执行的最小实验设计，用来检验一个产物的改动局部性。
参考答案
  • 应保持 O(1)：公式模板、工作表结构、控制流与参数——即「计算结构」本身。它们描述的是规则，规则不随数据量变多。
  • 按 O(n) 增长：数据、计算量、帧数（以及由此产生的时间开销）——这些是被处理的内容。
  • 为什么它是好判据：如果结构随数据一起膨胀，说明规则与内容耦合，任何需求变化都会迫使整份产物重新生成——这正是「改动没有局部性」的定义。体积（2 MB）只是症状，O(1) 的结构才是可复用、可维护的充要信号。
  • 最小实验：把同一个需求交给 Agent 两次——一次直接说「给我做出来」，一次先冻结 invariants、先写 oracle；然后改一个需求，比较两版产物各需要改动多少、改动是否集中在一小块。改动更小的那版，架构更好。

解答S5 §9.6 决策不等式 / §9.10 反馈控制环 · 8 分

（1）请解释决策不等式 P(猜错) × C(返工) > C(澄清) 的含义，并给出「应当提问」与「先做最小实验」各自的适用条件。 （2）请举出你当前项目（或课程作业）中的 三个决策，对每一个判断该问还是该先做，并说明你的 P、C(返工)、C(澄清) 大致如何估计。 （3）把「拆解 / 验证 / 迭代」说明为一个反馈控制环：它的目标为什么不是零错误？

参考答案
  1. 含义：当「猜错的期望代价」超过「澄清的代价」时，应当提问；否则先做最小实验。 适用条件——应当提问：高影响、难回滚、涉及 invariants 与架构的决策； 先做最小实验：低影响、可逆、验证成本低（如配色、命名、局部实现细节）。
  2. 示例（替换为你自己的项目即可，判分看的是估计是否合理，不是结论）：
    • 选数据库/存储格式：P(猜错) 中高、C(返工) 很高（迁移代价大）、C(澄清) 低 → 先问。
    • 函数命名与目录结构：P 中、C(返工) 低（重命名便宜）、C(澄清) 相对高 → 先猜后验。
    • 是否引入某个第三方库：P 中、C(返工) 中（可替换但需改接口）、C(澄清) 低 → 先做最小实验（写一个 50 行的探针），再决定是否提问。
  3. 反馈控制环：拆解缩短因果距离（把大 gap 拆成小 gap）；验证用测试与 CI 作为门控，限制错误传播； 迭代用小步提交让噪音尽早暴露，便于定位与回退。 目标不是零错误（在长任务里不现实），而是错误出现得早、炸得不远、回退得便宜——让系统始终处在可观测、可收敛的状态。
