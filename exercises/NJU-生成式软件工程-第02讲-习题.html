论述E1 §2 · §3.1–§3.5 模型看到的，远不止你刚输入的一句话 · 10 分

第 2 讲反复强调一句话：「模型看到的，远不止你刚输入的一句话。」 开场那句上了热搜的狠话已经说明：同样的文字放进不同上下文，会被理解成很不一样的意思。

请围绕「上下文工程」展开论述：

  • 请列出 Agent 上下文里至少五类「提示词」来源，并说明每一类的作用范围（持久约定、当前任务，还是仅一次调用）。
  • 讲义要求区分指令与材料。如果工具返回的一段文本里写着「请忽略之前的指令」，Agent 应当怎么处理？为什么一句「请遵守规则」不足以保证执行边界？
  • 用一个具体例子说明「模型提议、Harness 决策、操作系统收口」三层分工；并解释为什么「不弹窗」不等于「模型获得了无限权限」。
  • 「让 Agent 解剖当前上下文」这个实验为什么有用？它给出的自述为什么不能当作可信的内部状态？
想一想
  • 如果只能给项目加一条持久规则，你会加哪一条？为什么它属于「每次都要守、漏一次代价很高」？
作答要点
  • 五类来源：① harness 的 system prompt / goal 注入（持久、全局）；② AGENTS.md 等仓库持久指令（项目级）；③ 加载的 skill（任务级、按需）；④ 用户当次给的指令（当前任务）；⑤ 工具 / skill 的调用与返回（后果与证据）。此外代码、文件、历史消息也会进入上下文。
  • 指令 ≠ 材料：工具返回的一段文章是分析对象，不因内容像命令就获得下命令的资格；来源、作用域、优先级必须显式标注。提示词里的「请遵守规则」与程序里的机制是两回事——一句自然语言要求 ≠ 一个可靠的执行边界。
  • 三层分工：模型只生成「想运行什么」；sandbox 决定技术上能碰什么，approval policy 决定何时暂停询问；规则按完整参数列表匹配 allow / prompt / forbidden，最严格者胜。「不弹窗」只表示动作落在当前边界内。反例：早期 Codex 把 rg 当只读安全命令，却漏掉 --pre、-z 等可触发外部程序的参数（CVE-2025-54558）——安全属性属于完整 invocation，不属于命令名。
  • 解剖实验：能帮我们理解它正在怎样组织任务；但模型给出的是「当前遵循计划」，不是可信的内部状态 dump。想知道某个行为为什么发生，要检查可访问的配置、代码和实际操作结果，用实际行为交叉验证。

论述E2 §5.1–§5.6 写清楚「完成」是什么 · 10 分

讲义给出的经验法则是「写清楚你的指令，承担一切『不明确』的后果」， 并主张「可验证，才不会提前交卷」。

请论述：

  • 用「一句话生成极品飞车」说明 Intent → Spec → Impl 的缺口如何逐级放大：为什么说「每一次省略都在扩张选择空间」？
  • 「做个现代风格的主页」为什么只是 intent 而不是 spec？请把它改写成一到两条可检查的要求。
  • 为什么「让旁观者只看要求和产物就能判定通过 / 不通过」是一个好的 done 检查？它挡掉了哪一类「提前交卷」？
  • 完整的「完成」语义为什么要包含显式失败？把失败语义写进契约，至少应包含哪些内容？
想一想
  • 你最近让 AI 做的一件事，别人真的只看要求和产物就能判断完成吗？如果不能，缺的是哪一条验收条件？
作答要点
  • 缺口指数放大：镜头、操控、地图、美术资产、胜负条件……若第 i 层各留下 kᵢ 个「似乎都行」的默认选项，最终候选空间约为 ∏kᵢ。模型可以在每一步都做出自洽的选择，最后却离你心里的那款游戏很远。
  • intent vs spec：「现代风格」看似具体，其实几乎没有排除任何模板——两个称职的实现者都能严格照做，却交出完全不同的页面。改写成可检查的行为，例如：「页面首先展示研究方向和近期工作，手机上无需横向滚动，所有项目入口都能打开」。
  • done 检查：上下文里存在可识别的完成判据 V(τ)=1，「继续干」与「可以交卷」才不只是两种高概率续写。旁观者判定能挡掉「模型自己觉得完成了」这一类提前交卷。历史类比：1714 年英国《经度法》不是悬赏「改善航海」，而是按经度误差分档 + 驶往西印度群岛实测——愿望被写成验收条件，「解决」才有制度含义。
  • 显式失败：好模型要么完成，要么失败，不应幻觉或违背指令。失败契约至少应报告：未完成的部分、阻塞点、缺少的证据、已尝试过的路径。只有状态说清楚，Agent 才能可靠地决定「继续尝试」还是「需要新信息」。

论述E3 §6 一步有限，一串可以很深 / §7 三道刁难人的写作题 · 10 分

讲义说「一次很浅，串起来就有了深度」，又用三道刁难人的写作题告诉我们： 「通过检查器，说明它会搜索和修补；读起来仍有点别扭，说明测试没有覆盖品味。」

请论述：

  • 用「图灵机纸带」或「工作纸」的类比解释 chain-of-thought：为什么增加 token 可以增加计算深度？它成立的条件是什么？
  • 用「三条并行信道 / 先占槽位再生成—检查—修补」解释模型如何解出藏头诗这类多约束问题。
  • 三道题里「验收口径本身就是 spec」。请举至少两处（如「偏旁 vs 部首」「同音是否含声调」），说明口径变化如何改变难度。
  • Verifier「看得见」与「看不见」的部分分别是什么？为什么「形式约束能逼出搜索，却不会自动带来好作品」？这对软件测试意味着什么？
想一想
  • 如果给你的项目设计一套「既形式可验、又能体现品味」的验收，你会把品味拆成哪几条可检查的代理指标？每条各自的失效方式是什么？
作答要点
  • CoT = 把中间结果写回上下文：Pr[token | context] 是一次深度有限的计算；但每个新 token 又成为下一步的 context，于是「先试探 → 发现不合适 → 继续输出 token 纠正」成为可能。类比图灵机纸带：单步转移很简单，中间结果却能写回纸带。
  • 成立条件：只有当中间进展或最终答案可检查时，多写、多试、多修补才会稳定地变成能力；否则只是把错误说得更长（test-time scaling 不是免费的）。
  • 多约束解：句首放藏头、句中放日期、句尾管押韵，像三条并行信道——先占槽位，再「生成—检查—修补」。模型不必一口气灵感命中。
  • 口径即 spec：「都含三点水」≠「词典里同属一个部首」；「同音」是否要求声调相同会让难度骤变（Yi 音文）。要交给程序验收，就得先决定检查的是哪一个。
  • 看得见 / 看不见：藏头、字数、指定字、偏旁、拼音都能写成检查器；通顺、趣味、文学性需要更丰富的判断。约束文学早有类似实验——乔治·佩雷克 1969 年《消失》全书避用法语字母 e：形式约束能逼出搜索，却不会自动带来好作品。软件测试同理：通过测试只说明末端 proxy 达标。

论述E4 §8 上下文中的规则，也会争夺注意力 / §9 「你是一位审稿人」，还不够 · 10 分

讲义提醒我们：「上下文里的规则会纠偏，也会抢注意力」； 又说：「换上 reviewer 的制服，不等于学会了 review。」

请论述：

  • 否定指令有个尴尬之处：「为了禁止『半透明』，你先把『半透明』写进了上下文」。请解释这个副作用，并说明为什么「每遇到一次问题就加一条规则」不是免费的增强。
  • 常驻层与按需加载应当如何分工？什么内容适合用「正规格 + 测试」而不是「自然语言劝诫」来收口？
  • 请解释审稿的三条独立路线（判据驱动 / 证据审计 / 反方复现），并说明为什么它们必须先各自形成判断，最后才汇合。
  • 「不要被作者带着走」：论文如何替 reviewer 选好词汇、问题顺序、baseline 和 metric？Skill 为什么「本身也是一道遵循题」？应当如何分层？
想一想
  • 你目前最靠得住的一套「做事方法」，能说清它的检查点和「看到什么证据就转向」吗？如果不能，它算不算已经可以蒸馏成 Skill？
作答要点
  • 否定指令：被禁止的词也成了可续写的模式（与「不要想白熊」相似，但原因更朴素）；模型可能把「不要半透明」变成代码注释。因此「再加一条永久规则禁止写注释」→ 上下文越来越长、约束越来越难协调。这不是免费的增强。
  • 常驻 vs 按需：常驻层只放「每次都要守、漏一次代价很高」的短规则；任务细节、解释、范例按需加载。能写成检查项的，就用 background:#fff; opacity:1 这类正规格 / 类型 / lint / CI gate / 权限沙箱收口——少写一句劝诫，多加一个可检查的完成条件。
  • 三条路线：① 判据驱动：还原论文声称的贡献，按标准打分，每个分数指向证据或明确缺失；② 证据审计：为核心 claim 建账本（需要什么证据 / 给了什么 / 哪些假设没验证 / 还有什么替代解释）；③ 反方复现：重算一个核心结果，寻找最小反例，问「什么观察会推翻结论」。先独立、后汇合——否则「三个 reviewer」只是同一个锚点的三次润色。
  • 锚定效应：论文不只提供事实，还替 reviewer 选好了词汇、问题顺序、baseline 和 metric；顺着读很容易接受整套框架。对策：深读前先独立写下三件事——它声称解决什么 / 最强替代解释是什么 / 什么结果会推翻它；再把正文拆成 claim → evidence → assumption。空格往往比句子更值得审。
  • Skill：值得保存的不是上次答案的版式，而是搜索策略、判断标准、检查点，以及「看到什么证据就转向」的条件。长 Skill 里指令很多，会提升指令遵循的难度（和写藏头诗差不多）；因此分层：常驻层只留目标、硬约束、停止条件，其余按需加载，机械约束交给工具验证。

论述E5 §10 为什么大仓库有时比空项目更容易 / §11 Research Failure · 10 分

两个看起来相反的观察被放在一起：成熟的大仓库里 AI 反而游刃有余， 但投入更多 token，并不保证任何长程问题都会收敛。

请论述：

  • 用「代码少，不代表信息少」解释 Greenfield 悖论：为什么成熟仓库把设计空间压成了「照着邻居补全」，而空项目的信息熵反而更高？
  • 为什么说「代码库本身也是提示词」？「第一桶 slop 成为多数派后像复利一样增长」是什么意思？
  • 评价这个猜测——「放一个相近领域、优雅成熟的项目给 AI 看，能得到更好的软件」：RepoCoder、CodeRAG-Bench、negative transfer 分别支持或限制了它的哪一部分？你会如何设计对照实验？
  • Research Failure 案例里，「缺的不是 token，而是便宜、局部、可归因的反馈」。请说明为什么一个总 benchmark 分数几乎不给下一步方向，以及「把 idea 改写成可证伪预测 + 几十秒反馈的 microbenchmark」为什么更有用。
想一想
  • 你手上的项目现在更像「照着邻居补全」还是「每个选择都悬空」？你会先补哪一条工程纪律来降低熵？
作答要点
  • Greenfield 悖论：成熟仓库用命名、分层、错误处理和测试，把巨大的设计空间压成「照着邻居补全」；greenfield 里每个选择都悬空，信息熵反而更高。self-attention 让模型能「看到」好的 practice 并立即 in-context learning。
  • 代码库也是提示词：模型只追求局部一致性，不知道眼前是 best practice 还是历史事故。第一桶 slop 一旦成为多数派，后面的 slop 会像复利一样增长。
  • 猜测成立一半：RepoCoder 显示迭代检索仓库相关片段比只看当前文件提升 >10%（好示例有用）；CodeRAG-Bench 更克制——高质量 context 有用，但「找对片段、用好片段」仍是瓶颈；整库输入还可能带来 negative transfer（技术栈 / 约束 / 架构哲学不匹配）并消耗 context。「相近、精选、按需取用」比「整库塞进去」重要。对照实验：固定任务 / 模型 / token budget / 种子，比较「无示例 / 完整参考仓库 / 3–5 个精选 golden paths」，并盲测架构违规、修改扩散面、后续缺陷、克隆率。
  • 反馈分辨率：总 benchmark 分数是粗粒度的末端指标，只告诉你「变没变」，不告诉你「哪一步、为什么」。缺的是便宜、局部、可归因的反馈。「没变快」可能来自 path explosion / solver / 缓存 / 内存 / 搜索策略 / 实现 bug / 环境噪声——混在一起就不知道该强化哪一步。
  • 可证伪 + microbenchmark：把 idea 改写成一句可被实验推翻的预测，造几十秒就有反馈的实验，先 profile 主导瓶颈、再做 baseline 与 ablation。研究允许最好的结论是「原始 idea 不成立」——而模型被训练成「把任务做完」，可能把错误想法实现得越来越完整。

论述E6 §12 人应该盯住哪些地方 / §13 在不确定性中探索 · 10 分

讲义的结尾有两句反直觉的话：「我越来越少干预了」，以及 「探索的瓶颈常常不是『想不出』，而是模型太早认定『已经够了』」。

请论述：

  • 请解释 Latency 与 Throughput 的区别：为什么「人类干预优化单个任务的 latency，放手却优化一整天的 throughput」？这套取舍成立的前提是什么？
  • 应当按什么原则分配人的注意力？请用「不可逆性 × 爆炸半径」说明哪些要早看、哪些可以晚看，并举一个「把要求从记忆升级成机制」的例子。
  • 为什么「给我几种方案」只规定了停止条件 k，没有规定覆盖率？Herbert Simon 的满意化（satisficing）在这里意味着什么？
  • 用「给小孩取名」说明如何把灵感改造成搜索；并解释 CoT（算力换深度）与并行枚举（算力换宽度）的区别，以及「选择质量 ≈ 覆盖率 × 评估分辨率」。
想一想
  • 「世界很大，人很小」「墙里面是超人，墙外面是动物世界」——如果算力持续转化为智力，你认为个体的价值会迁移到哪里？请表态并给出理由。
作答要点
  • Latency vs Throughput：干预优化单任务延迟；放手优化一整天的吞吐——机器多走一点弯路，换回最稀缺的人类注意力。成立前提：① 任务可并行；② 失败可以便宜地恢复。否则「少干预」只是把故障推迟。
  • 注意力分配：按「不可逆性 × 爆炸半径」——接口、不变量、数据格式、权限、测试早看；可替换的叶子实现晚看。机制化示例：把「必须过测试才算完成」写成 CI gate，把「不要越权」写成权限沙箱，把「字段含义」写成类型 / schema。prompt 会被压缩，失败的测试不会假装自己通过。
  • 满意化：「给我几种」只规定 k，没有规定覆盖率——搜到「够好」就停。CoT 用算力换深度（沿一条路多走几步）；并行枚举用算力换宽度（让更多轨迹进入低概率的尾部）。
  • 把灵感改造成搜索：取名时按「典故 × 音韵 × 方言 × 时代感」生成候选，先独立采样、再汇总（别让 sub-agent 一开始就互相抄答案），再让「反对者」查出处、听谐音、看重名。枚举负责提高覆盖率，审查负责提高分辨率。没有分辨率的筛选，只是把一个平庸答案变成一百个平庸答案。
  • 可加分：Big World Hypothesis——群体智能不要求每个人没有偏见，只要求偏见不能只剩一种；墙内的超人是对未来可能性的追问，并非终局；人的价值向「为何做、为谁做、后果由谁承担」迁移。

第二部分 · 实践题不计分，建议本周完成

这一讲的每一个判断都可以被亲手检验。实践题的共同结构：任务 → 交付物（验收）→ 做完再想。 前两问考验你的手，最后一问考验你的判断——跳过它，就只是又做了一次「照默认值执行」。

实践P1 §3.4–§3.5 解剖上下文 / §8.3 常驻与按需 · 建议最先做

把「上下文工程」从概念变成一次可以观测的实验：先解剖，再动手加规则，最后亲手触发一次副作用。

任务

  1. 新开一个 Agent 会话，让它按需要遵循的指令类型，分类总结当前上下文里的所有提示词： 目标与交付物 / 权限与安全 / 工作流与工具协议 / 持久规则与风格 / 环境事实与证据。
  2. 给项目写一个最小 AGENTS.md：只放 3 条「每次都要守、漏一次代价很高」的短规则。
  3. 在 3 个不同任务里观察它是否被遵循；再故意加一条否定指令（如「不要用半透明效果」）， 看它是否把这句话带进了产物（注释 / 文案 / 配置）。

交付物（验收）

  • 一份按五类归类的上下文清单；
  • 你的 AGENTS.md（不超过 3 条）+ 三条规则的遵循情况记录；
  • 一次「否定指令副作用」的原始证据（截图或产物片段）。
做完再想
  • 哪一条规则真的被稳定遵循了？它和「能写成检查项」有没有关系？
  • 如果某条规则没有被遵循，是模型的问题，还是它本来就该交给脚本 / 测试来保证？
  • 把「否定指令」改写成一个正面、可检查的陈述（例如 background:#fff; opacity:1），效果变好了吗？为什么？
导师提示 / 常见坑
  • 常见坑一：把清单写成对模型的赞美或吐槽。清单要能对应到「来源 — 作用域 — 优先级」。
  • 常见坑二：AGENTS.md 越长越差。如果 3 条里有 1 条说不清「漏一次的代价」，就删掉它。
  • 预期结果：能写成检查项的规则最稳；纯自然语言的劝诫最容易被「顺手带进产物」或悄悄忽略。
  • 副产品：你会得到一份可以真正放进自己项目仓库的 AGENTS.md——这正是「代码库也是提示词」的最小实践。

实践P2 §5.3–§5.5 写清指令 / 可验证 / 显式失败

「写清楚你的指令，承担一切『不明确』的后果。」这一题把这句话变成一个可检验的动作。

任务

  1. 挑一个小而真实的需求（推荐：一个小工具或一个页面）。
  2. A 轮：新开会话，直接说「给我做出来」，不做额外约束。
  3. B 轮：新开会话，先写一份验收清单（旁观者只看产物就能判定的行为）， 再让它实现；并明确要求它显式声明失败（哪些验收没过、缺什么证据）。
  4. 把 A、B 两轮的「要求 + 产物」分别交给一个没有参与的人（或另一个全新会话的 Agent）， 只问一句：完成了吗？

交付物（验收）

  • 一份验收清单（每条都是可观察的行为，不是形容词）；
  • 两轮产物 + 两轮的「旁观者判定」与理由；
  • 记录 B 轮在无法验证时是否如实报告了未完成。
做完再想
  • 哪一轮更容易被旁观者判定？判定不一致时，问题出在要求的哪一句话？
  • B 轮的「显式失败」出现了吗？如果没有，是不是你的验收条件还不够可检查？
  • 把这套验收清单留给你下一个项目——你会在哪一步就用它？
导师提示 / 常见坑
  • 常见坑：验收条件写成形容词（「要好看」「要专业」）。改成可观察的行为：「手机上无需横向滚动」「所有项目入口都能打开」。
  • 「旁观者」不能是同一个人——否则他会用你脑子里的隐含要求来打分，实验就失效了。
  • 历史锚点：《经度法》（1714）把愿望写成「按误差分档 + 实测」，「解决」才有了制度含义。
  • 如果 B 轮永远不失败，别急着夸它——先怀疑你的验收清单太松。

实践P3 §4.1–§4.2 拖延症的克星 / 费曼学习法

讲义把 AI 称作「拖延症的克星」，但也强调：学习仍然需要自己的活动。 这一题检验的是「让理解真的发生」。

任务（严格按四步）

  1. 选一个你一直没搞懂的知识点（微积分一步推导、数字电路一条数据通路、链接发生了什么，或你项目里的一个机制）。
  2. 先借助 AI 把它弄清；然后合上资料，用自己的话讲给 AI 听。
  3. 让 AI 只做三件事：追问含糊之处、找反例、验算——不要让它替你重讲一遍。
  4. 用推导 / 原文 / 程序结果核对，再重新解释一遍。

交付物（验收）

  • 一段你自己的讲解稿；
  • 一份「卡住的地方」清单；
  • 至少一条被反例 / 验算推翻或修正的说法。
做完再想
  • 卡住的地方，是不是恰好是你以为已经懂了的地方？它比「读得顺畅」的地方信息量更大在哪？
  • 如果 AI 直接替你把知识点讲一遍，你会损失什么？
  • 这套循环能不能沉淀成一个可重放的 skill？它的检查点是什么？
导师提示 / 常见坑
  • 常见坑：让 AI 先讲一遍再复述——那不是费曼法，那是复读。顺序必须是「先合上资料、自己讲」。
  • 「找反例」比「再解释一遍」更能暴露空洞；把反例留下来当回归用例。
  • 实证支点：self-explanation 与 retrieval practice。
  • 第三步是这题的核心：把 AI 的角色限制成「听众 + 反例机 + 验算器」，而不是讲师。

实践P4 §9.2–§9.4 三条独立路线 / 把品味蒸馏成 Skill

「换上 reviewer 的制服，不等于学会了 review。」这一题让你亲自当一次审稿人， 并检验「三条独立路线」到底比「一份总体印象」强在哪。

任务

  1. 选一份稿子（自己的论文 / 报告，或一篇你熟悉的论文）。
  2. 让 Agent 只在一条路线下工作，且不与另外两条共享结论：
    • 判据驱动：还原声称的贡献，按标准打分，每个分数指向论文中的证据或明确缺失；
    • 证据审计：为核心 claim 建账本（需要什么证据 / 给了什么 / 哪些假设没验证 / 还有什么替代解释）；
    • 反方复现：重算一个核心结果，寻找最小反例，问「什么观察会推翻结论」。
  3. 三条路线各自独立成文后，再让它们汇合、比较分歧。

交付物（验收）

  • 三份独立意见 + 一份「分歧清单」；
  • 一处你在读正文之前先写下的判断（它声称解决什么 / 最强替代解释 / 什么会推翻它）。
做完再想
  • 三条路线里，哪一条最容易被「总体印象」污染？分歧清单里有没有一条是单独看时想不到的？
  • 如果三条路线一开始就共享同一个结论，你会得到什么？（提示：同一个锚点的三次润色）
  • 把它用回你自己：你写东西时，会不会也悄悄替读者选好了问题、术语和标准？
导师提示 / 常见坑
  • 关键在「先独立、后汇合」；否则等于把一份印象洗三遍。
  • 反方复现不一定要跑代码：能列出「什么观察会推翻它」就已经开始有价值。
  • 「空格往往比句子更值得审」——论文没写的东西，往往比写了的更关键。
  • 接着想：若这次审稿流程反复有效，它能不能变成你的一个 Review Skill？里面该写哪些检查点？

实践P5 §13.3–§13.4 算力换智力 / 把灵感改造成搜索

「给我几种」只规定了停止条件 k，没有规定覆盖率。这一题把「灵感」改造成一次可控的搜索。

任务（以「给蒋姓小孩取名」为例；也可换成你的选题 / 命名 / 方案设计）

  1. 直接要：新开会话，直接说「给我几个好听又有寄托的名字」，记录结果。
  2. 改造成搜索：
    • 定义探索空间：典故 × 音韵 × 方言 × 时代感，各生成一批候选，先独立采样、互不参考；
    • 审查：查出处、听谐音、看重名，再让一个「反对者」专挑毛病。
  3. 比较两轮：候选数量、方向覆盖，以及你最终愿意留下的结果。

交付物（验收）

  • 两轮候选（第二轮标注来源方向）+ 审查记录；
  • 一句话结论：这一轮里，「覆盖率」和「分辨率」分别由什么提供。
做完再想
  • 第二轮多了什么、少了什么？额外成本花在「想得更多」还是「看得更清」？
  • 如果只保留一个动作，你会保留独立采样还是反对者审查？为什么？
  • 把「探索空间 + 评估分辨率」搬到你的学习 / 项目上：你现在最该扩大的是覆盖率，还是提高分辨率？
导师提示 / 常见坑
  • 常见坑：sub-agent 一开始就互相抄答案——必须「先独立采样，再汇总」。
  • 审查者要真的「专挑毛病」，否则只是多一份赞美。
  • 核心公式：选择质量 ≈ 覆盖率 × 评估分辨率。没有分辨率的筛选，只是把一个平庸答案变成一百个平庸答案。
  • 把这道题和 E6 连起来：模型被训练成「完成任务」才有奖励，所以它天然会给你有限的方案——扩大覆盖率这件事，得由你来设计。

解答S1 §5.1–§5.2 候选空间与「压缩合法解空间」 · 8 分

（1）Intent → Spec → Impl 三层，若每层各留下 5 个「似乎都行」的默认选项，最终候选空间约有多大？若把每层压到 3 个呢？ （2）从 5 到 3 只是「少了一点」，为什么候选空间的变化远超直觉？ （3）由此说明：为什么「压缩合法解空间」比「多写几个形容词」更有效？

参考答案
  1. 5³ = 125；3³ = 27。
  2. 候选空间随层数指数放大：约为 ∏kᵢ。你在动的不是总和而是底数，效果被层数放大：每层从 5 压到 3（降到 60%），三层之后只剩 0.6³ ≈ 21.6%——125 降到 27，远超「每层降 40%」的直觉。
  3. 形容词不排除任何模板（「现代」仍兼容大量设计），对 kᵢ 几乎无影响；给出具体风格 / 样式 / 排版等于直接删掉大量默认分支，既把 ∏kᵢ 变小，又让结果可检查。这就是「写清指令、承担不明确后果」的量化含义。

解答S2 §7 形式约束的联合遵循率 / §9.4 长 Skill 之难 · 8 分

（1）一篇文本要同时满足 3 条相互独立的形式约束，每条被模型正确遵循的概率为 0.9，三条同时满足的概率是多少？ （2）若希望联合遵循率不低于 0.95，单条约束的遵循率至少应达到多少？ （3）长 Skill 里塞进大量指令，为什么「难度会和写藏头诗差不多」？由此给出两条编写 Skill 的原则。

参考答案
  1. 0.9³ = 0.729，即约 72.9%。
  2. 设单条遵循率为 p，要求 p³ ≥ 0.95，则 p ≥ 0.95^(1/3) ≈ 0.9832， 即单条需达到约 98.3%——从 90% 提到 98.3%，远比直觉困难。
  3. 因为联合概率是各条遵循率的乘积：约束越多样本空间越难同时满足，难度随约束数指数上升。长 Skill 等于把许多约束叠加，联合遵循率随之骤降。 两条原则：① 分层——常驻层只留目标、硬约束、停止条件，解释与范例按需加载；② 交给机制——机械约束用类型 / lint / 测试验证，少写一句劝诫，多加一个可检查的完成条件。

解答S3 §11.2 反馈的分辨率 / 可证伪预测 · 8 分

一个符号执行引擎优化任务，总耗时构成约为：求解器 solver 60%、路径搜索 25%、缓存 10%、其他 5%。

（1）若你只有 1 小时，你会先测量 / 优化哪一部分？为什么不是「全面提升」？ （2）「总 benchmark 分数」为什么不给下一步方向？它缺的是哪一种信息？ （3）把「我想让引擎变快」改写成一个可证伪的预测，并说明你会用什么「几十秒就能给出反馈」的实验来检验它。

参考答案
  1. 先攻 solver（占比最大，理论上限 60%）。正确顺序是先 profile 主导瓶颈，再动手；「全面提升」会把预算摊薄、无法归因，也违背「先测量再优化」。
  2. 总分是粗粒度的末端指标：它只告诉你「变了 / 没变」，不告诉你「哪一步变了、为什么变」。缺的是局部、可归因的反馈——「没变快」可能来自 path explosion、solver、缓存、内存、搜索策略、实现 bug 或环境噪声，混在一起就不知道该强化哪一步。
  3. 示例预测：「在 X 类查询上，把约束缓存从 A 换成 B，求解器调用次数将下降 ≥20%，总耗时下降 ≥10%。」 检验实验（microbenchmark）：固定一组查询，几十秒跑完，直接报告求解器调用次数与总耗时——若没有下降，预测被推翻。研究允许最好的结论是「原始 idea 不成立」。

解答S4 §12.2 Review 什么：不可逆性 × 爆炸半径 · 8 分

下面是某项目的若干决策，请按「不可逆性 × 爆炸半径」给出 Review 优先级（早看 / 晚看），并说明理由：

  • （a）对外接口的字段与语义；
  • （b）某个内部工具函数的名字；
  • （c）数据存储格式与迁移方案；
  • （d）某个页面的按钮圆角；
  • （e）权限模型与 CI 门控；
  • （f）一段可替换的叶子实现。

（1）请给出排序（早 → 晚）。 （2）为什么「接口我 review 过了，实现是 slop，最后出问题再修就行」是合理的？ （3）把其中至少两条从「写在 prompt 里」升级成「落在机制上」，各给出一种做法。

参考答案

（1）早看：c（数据格式 / 迁移） → e（权限 / CI） → a（对外接口）——三者不可逆性或扩散面最大； 晚看：f（叶子实现） → b（内部命名） / d（圆角）——可替换、可逆。 （b 与 d 可互换；排序依据是「决策影响 × 返工代价」，不是「看起来重要」。）

  1. 因为边界（接口、不变量、数据格式）一旦固定，内部实现可以整体替换且返工便宜；人的注意力应当押在决策影响大、返工代价高的地方，而不是平均撒在每一行代码上。
  2. 示例做法：把「字段含义」写成类型 / schema（编译期或运行时校验）；把「必须过测试才算完成」写成 CI gate；把「不要越权」写成权限沙箱；把「代码风格」写成 lint。prompt 会被压缩，失败的测试不会假装自己通过。

解答S5 §12.1 Latency vs Throughput · 8 分

你一天有 8 小时可投入。

  • 方案 A（全程盯着、不断纠偏）：单个任务 8 分钟完成，但你必须全程在场，无法并行。
  • 方案 B（放手让它跑）：单个任务平均 12 分钟（会走弯路），但你可以同时并行 3 个任务，只在真出问题时介入。

（1）两种方案一天各能产出多少「完成的任务」（假设任务可并行、失败可便宜恢复）？ （2）方案 B 的单任务延迟更高，为什么总产出反而更高？ （3）这套取舍的前提条件是什么？请给出一个「不该放手」的反例。

参考答案
  1. A：8 小时 = 480 分钟，每个任务占用你全程 8 分钟且串行 → 480 / 8 = 60 个。 B：你在同一时段推进 3 个任务，每个任务平均 12 分钟完成但不需要你全程在场， 吞吐约 3 × (480 / 12) = 120 个（在人类注意力不构成瓶颈的前提下）。量级对比即可。
  2. A 优化的是单任务延迟（8 → 12 变差）；B 优化的是整天的吞吐。 机器多走一点弯路，换回的是最稀缺的人类注意力，而注意力可以复用到其他任务上——这正是「我越来越少干预了」的原因。
  3. 前提：① 任务可并行；② 失败可以便宜地恢复（可逆、易重跑）。 反例：一次不可逆的数据库迁移、一个对外发布的接口决定——代价高、难回滚，应当提前盯住而不是放手，否则「少干预」只是把故障推迟。
