0. 一页纸总结#

第 1 讲留下的问题是：Agent 已经能做很多事，我们怎样才能驾驭它？第 2 讲从最常见的交互方式——自然语言指令——出发，讨论怎样让模型理解目标、遵循要求，以及在没有确定答案时继续探索。

一句话要点
开场「没有 token 的 CS 学生应该立即退学」上了热搜；课堂上这句话要推动的是立即实践，不是真的退学。同一句话离开现场、只剩截图，就只剩「狠」。
提示词 ≠ 对话框里的那句话Agent 看见的是整个上下文：system prompt、AGENTS.md、加载的 skill、用户指令、工具调用与返回，还有代码、历史消息与文件。
从「提示词工程」到「上下文工程」关心的不是一句话怎么写，而是每次决策前，哪些 token 以什么来源、顺序和作用域出现。
写清楚「完成」越明确、越可验证的要求，越可能得到满意的结果。经验法则：写清楚你的指令，承担一切「不明确」的后果。
一步很浅，一串可以很深单次前向计算深度有限，但模型可以把中间结果写回上下文，用更多 token 换计算深度——这就是 chain-of-thought。
形式约束会逼出搜索藏头诗、十八字同偏旁、全同音文：模型通过检查器说明它会搜索与修补；通过测试不等于写得好，测试没覆盖品味。
上下文是争用资源规则会纠偏，也会抢注意力。否定指令很尴尬：为了禁止「半透明」，你先把「半透明」写进了上下文。
方法论决定 AI 的上限「你是 ICSE reviewer」只改变先验与输出形状；好的审稿要走判据、证据、反方复现三条独立路线。有效经验可蒸馏成 skill。
大仓库 vs 空项目成熟代码库替你做了很多决定，Agent 可以「照着邻居补全」；代码库本身也是提示词，第一桶 slop 会像复利一样叠加。
人的注意力怎么分配人少干预、把注意力换成一整天的吞吐量；按「不可逆性 × 爆炸半径」Review，把要求从「记忆」升级成「机制」。
在不确定性中探索「帮我考虑几种方案」只规定了停止条件 k，没有规定覆盖率。把灵感改造成搜索：先独立采样，再审查。选择质量 ≈ 覆盖率 × 评估分辨率。
未来算力成为生产资料——「砌一堵墙，墙里面是超人，墙外面是动物世界」。这是对未来可能性的追问，不是已经发生的终局。

1. 开场：一句狠话与它的上下文#

讲义开篇写道：不过，先处理一下第一讲留下的意外。

1.1 「没有 token 的 CS 学生应该立即退学」上了热搜#

第一讲里的一句话——「没有 token 的 CS 学生应该立即退学」——居然以一个非常意外的方式上了热搜，也引来了朋友们的问询。

当然不会真的让同学们退学。课堂上这句话要推动的是立即实践：不要把等待完美工具、等待别人给出评价，变成一直不开始的理由。离开现场，截图只剩下一句狠话，这本身也提醒我们，同样的文字放进不同上下文，会被理解成很不一样的意思。

1.2 现场成立，截图只剩「狠」#

一句只对现场成立的狠话，被截图以后就只剩「狠」了。

这本身就是本讲第一个例子：同一段文字，放进不同上下文，会被理解成很不一样的意思。当一句为了课堂现场而说的话被抽离现场、只剩截图时，语气、对象和意图全部丢失，剩下的只是一个刺激性的判断。

1.3 「不要把等待完美工具变成不开始的理由」#

既然出发点是推动「立即实践」，老师顺带回应了「用不起贵模型」的顾虑（幻灯片 2）：

  • Anyway，你们懂我不会真的让你们退学的——但如果不这么说，你们真的听不进。
  • （虽然说了也听不进。）
  • 而且 Token 也没那么贵。
  • 退一百万步讲，还有 ¥40 的豆包（含 GLM、DeepSeek 等）。

贵模型用不起，就用 ¥40 的；再不开始，就不是预算问题了。

2. 「提示词」从哪里来#

ChatGPT 普及了 Prompt，但没有发明它。（幻灯片 3）

  • 2019 年 GPT-2 的发布页面已经写下「prompting the trained model」：输入文本从「开头」变成了控制模型续写的条件。
  • 2020 年 GPT-3 把任务说明和 few-shot 示例都称为 prompt。
  • 2021 年，「prompt programming」和「prompt-based learning」成为研究对象。

我们习惯把给模型的输入叫作 prompt，中文称「提示词」。从语言模型续写文本的角度看，前面的文字既是开头，也是控制后续生成的条件。进入聊天界面以后，用户更容易把 prompt 理解成对话框里的一条要求——但这是被界面简化过的理解。

3. 模型看到的，远不止你刚输入的一句话#

3.1 提示词不止在对话框#

对 Agent 来说，指令分散在很多地方。以下都是提示词：

  • Harness 内部：system prompt、goal 模式注入等；
  • AGENTS.md 等持久指令；
  • 加载的 skills；
  • 你给的指令；
  • 工具 / skills 的调用和输出。

与此同时，代码、文件、历史消息和工具返回也会进入上下文。第一讲里的 Pr[token | context]，其中的 context 就包含这些内容。模型下一步做什么，受到整份上下文影响，而不是只由最后一句话决定。

3.2 指令与材料：来源、作用范围与优先级#

不过，不是所有 context 都是指令：代码、历史消息、工具返回也可能只是事实、状态或样例。

这里要区分指令和材料：工具返回的一段文章可能是分析对象，并不因此拥有给 Agent 下命令的资格。来源、作用范围和优先级，也属于我们组织上下文时需要考虑的事情。

幻灯片还点出一个容易被忽略的事实（幻灯片 5）：模型只看到 token 序列；system / user / tool 的边界、优先级和权限，都是 Harness 放进上下文、并在外部执行的。

3.3 从「提示词工程」到「上下文工程」#

所以，「提示词工程」逐渐扩展成了「上下文工程」：关心模型在做决定时能看到什么，哪些是目标，哪些是约束，哪些是证据，哪些只是过时的过程记录。

  • 「提示词工程」关心一句话怎么写；「上下文工程」关心每次决策前，哪些 token 以什么来源、顺序和作用域出现。
  • 目标是让 working set 足够小、足够新、带来源、可验证；上下文窗口装得下，不等于注意力用得好。
  • 到 Claude Opus 4.5 这一代，模型靠强化学习获得了极强的指令遵循能力，直接输出命令和工具调用，持续向目标推进。

写好一句话当然有用，但把相关文件、已有实现和验证结果放到合适的位置，往往同样重要。

3.4 立即行动：解剖当前上下文#

课堂提出了一个可以立即做的小实验——让 Agent 解释「谁在给它下指令」，按需要遵循的指令类型分类总结：

Prompt分析一下你上文中的所有提示词（包括系统），并按照需要遵循的指令类型分类总结。
  • 目标与交付物：要完成什么，何时算完成；
  • 权限与安全：能读写什么，何时必须确认；
  • 工作流与工具协议：先做什么，工具怎样调用；
  • 持久规则与风格：AGENTS.md、skills、语言和格式；
  • 环境事实与证据：文件、历史消息、工具输出。

冲突时再标出来源、作用域和优先级。这个实验可以帮助我们理解它正在怎样组织任务，但要记住：模型给出的是「当前遵循计划」，不是可信的内部状态 dump；想知道某个行为为什么发生，还需要检查可以访问的配置、代码和实际操作结果，用实际行为交叉验证。

3.5 「安全命令」是谁判的？#

例如，为什么有些命令执行前会询问用户，有些不会？不能只从「模型觉得安全吗」来解释。模型提议，Harness 决策，操作系统收口。

Codex 有一些细节：它认为「安全」的命令，不触发用户提示。这是怎么实现的？

  • 模型只生成「想运行什么」；sandbox 决定技术上能碰什么，approval policy 决定何时暂停询问。
  • 规则按完整参数列表匹配 allow / prompt / forbidden；简单 shell 链会被语法解析后逐条检查，最严格的结果获胜。
  • 因此「不弹窗」只表示动作落在当前边界内，并不等于模型获得了无限权限。
  • 真实教训：早期 Codex 把 rg 当作只读安全命令，却漏掉 --pre、-z 等可触发外部程序的参数。CVE-2025-54558 说明：安全属性属于完整 invocation，不属于命令名。

提示词中的要求与程序中的机制一起决定行为；一句「请遵守规则」，并不等于已经实现了一个可靠的执行边界。

4. AI 降低了开始学习的成本#

4.1 拖延症的克星：立即行动#

上下文工程听起来像开发者才需要关心的技术，但学生每天都能用到。（幻灯片 6）

  • AI 给我们的能力：立即行动，简直就是拖延症的克星。
  • 微积分，一个推导不想验算；数字电路，有个数据通路没看懂；计算机系统基础，链接没搞明白——这些统统可以立刻开始。
  • 老师学生时代的 self-motivated：「超高的容忍度」——愿意花很久寻找一个解释。
  • 现在学生的 self-motivated：用上飞轮，确保自己得到了正确的理解，并且重述给 AI。

现在可以立即把具体问题交给 Agent：给出一个最小例子，逐步推导，运行一段程序，再根据结果追问。过去的自我驱动，常常意味着对挫折有很高的容忍度；现在，我们可以把同样的精力投入到更快的尝试与反馈中。

AI 消灭的是「先试一下」的边际成本，不消灭真伪判断：提出最小问题 → 做最小检验 → 看反馈 → 更新理解。

4.2 费曼学习法：让 AI 当听众#

不是让 AI 再讲一遍，而是主动暴露缺口。（幻灯片 7）

  • 先合上资料，用自己的话讲；卡住的地方信息量最大。AI 的角色是追问、找反例和验算，查证后再讲一遍。
  • 这套飞轮有实证支点：self-explanation 与 retrieval practice。

学习仍然需要自己的活动。一个可行的循环是：先借助 AI 弄清一个问题，然后合上资料，用自己的话重述；让它追问含糊之处，找出反例，再用推导、原文或程序结果核对，最后重新解释一遍。复述时卡住的地方，往往比读答案时觉得顺畅的地方更能暴露知识缺口。

这可以理解为让 AI 做一个随时在场的听众。它帮助你开始，也帮助你发现哪里还没讲明白。真正推动理解的，是这个循环里不断变得具体的问题和不断接受检验的解释。

5. 写清楚「完成」是什么#

模型具有很强的指令遵循能力，但首先要有值得遵循的指令。上下文中的要求越明确、越容易验证，模型就越有机会判断自己距离目标还差什么；不明确的要求，则可能让它很早就认为已经完成。（幻灯片 10–15）

5.1 一句话生成极品飞车：Intent → Spec → Impl#

「一句话生成极品飞车」可以产生很漂亮的演示，是测试前端能力的好例子。但你心里想的，可能是有真实地图、特定美术资产、某种驾驶手感的赛车游戏。模型交出的，也许只是一个能移动、会碰撞、有速度感的网页。它未必在任何一步明显违背了指令，却在一连串默认选择之后，做出了另外一个产品。

这就是第一讲的 Intent、Spec 和 Impl 之间的缺口，而且 gap 会逐级放大漂移。镜头怎么跟随，车怎样转向，地图从哪里来，撞车以后发生什么，每一次省略都留下了选择空间。

若第 i 层各留下 k_i 个「似乎都行」的默认选项，最终候选空间约为 ∏ᵢ kᵢ。模型可以在每一步都做出自洽的选择，最后却离你心里的那款游戏很远。

模型可以把这些选择做得相互一致，但「一致」不意味着「正好是你想的」。

5.2 从「AI 味」到你的主页#

个人主页是另一个例子（幻灯片 14）。Bad：把品味留给默认值。

「我是蒋炎岩，根据我的公开信息，制作一个现代风格的个人主页首页……」你将会得到 AI 味。

「现代风格」看似具体，实际上几乎没有排除任何模板。模板、渐变、卡片和装饰都能被解释为现代风格；两个称职的实现者都能严格照做，却交出完全不同的页面——这仍然只是 intent。

Better：压缩合法解空间。补上「用具体风格、具体样式和排版」，就能得到接近预期的个人主页。颜色、字体、栅格、留白、组件和参考物共同构成设计语言。关键不是多写几个形容词，而是让选择可组合、结果可检查。几个形容词，通常不能代替设计。

5.3 写清指令，承担「不明确」的后果#

课堂的经验法则（Rule of Thumb）：

写清楚你的指令，承担一切「不明确」的后果。这样模型永远给你的是惊喜 😁

它要求我们意识到，没有说明的地方，实际上是把决定权交给了模型——授权模型用默认值替你做产品决策。并不需要把所有细枝末节都提前决定，但要知道哪些地方允许它自行发挥，哪些地方决定了产品是不是你要的。

历史类比（幻灯片 13）：1854 年轻骑兵冲锋中，山上的 Raglan 看得见目标，谷中的 Lucan 看不见；命令里的「那些炮」由执行者自行补全，轻骑兵最终冲向了错误的炮阵。不明确的指令，代价由执行者承担。

一个实用的检查办法是：让另一个人只看要求和最终产物，能否判断任务已经完成？「做得专业一点」很难判定；「页面首先展示研究方向和近期工作，手机上无需横向滚动，所有项目入口都能打开」就提供了可以检查的行为。不能完全机械判断的品味，也可以通过示例、对比和反馈逐步说明。

5.4 可验证，才不会「提前交卷」#

幻灯片 11 把这个问题概括为：可验证，才不会「提前交卷」。

  • 推论：越明确、越可验证的要求，越可能得到你满意的结果；不明确的要求，模型可能认为已经「满足」了。
  • 一个直接的检查：旁观者只看产物和工具结果，能否判定通过或不通过？如果不能，模型就没有稳定的 done。

把愿望改写成验收条件：1714 年英国《经度法》没有悬赏「改善航海」，而是按经度误差分档，并规定驶往西印度群岛实测。愿望被写成验收条件，「解决」才有了制度上的含义。

5.5 要么完成，要么显式失败#

完成的语义还包括失败。

  • 一个足够好的模型，要么完成，要么失败，不应该幻觉或违背指令。
  • 如果你的指令不过长，现在的模型基本足够好。
  • 可以把失败语义写进契约：只有测试或可检查证据通过才算完成；无法验证时，报告未完成、阻塞点和已经尝试的路径。

如果关键条件无法验证，合理的结果应当是报告哪里没完成、缺少什么证据，而不是交出一段肯定的总结。只有把这些状态说清楚，Agent 才能更可靠地决定继续尝试，还是需要新的信息。

5.6 新分工：人定义问题，AI 搜索实现#

幻灯片 15 把本课的主线画成一条新分工：

  • Intent → Spec → Impl：明确你的意图，需要你对产品领域的知识；把意图变成设计，需要你对软件工程的知识；实现反而多数可以交给 AI，它已经超过中级程序员了。
  • 可以把边界画在「搜索」和「判定」之间：人定义目标 G 与验收器 V，AI 搜索实现 x，直到 V(x)=1。

Impl 变便宜，判断没有。

Brooks 在 1986 年区分了软件的 essence 与 accident：困难在于构造、规格化、设计和测试概念结构，而不只是把它表示成代码。（No Silver Bullet）实现可以外包；验收标准和失败责任不能一起外包，否则 AI 优化的是它猜到的代理目标，不是你的产品目标。

6. 一步有限，为什么还能完成复杂任务#

一个疑问随之而来：如果模型只是反复计算下一个 token 的概率，它怎样同时满足很多约束？（幻灯片 16）

6.1 把输出当作可写的工作纸#

一次模型前向计算的结构和深度是有限的。它不会在这一瞬间任意增加计算步骤。

Pr[token | context] 是深度非常有限的计算。即使今天的 Mixture-of-Experts，所谓「专家」也只是表示空间上的分段函数，并不是坐在模型里的多个小人。大部分时候，接下来若干个「简单」 token 都是高概率确定的；一次前向计算不可能凭空完成复杂任务。

但模型学会了利用上下文思考：遇到不确定之处，不直接猜答案，而是先试一试；错了，还可以继续输出 token 纠正。每个新 token 又成为下一步的 context，这就是 chain-of-thought。

可以把它类比成图灵机的纸带：单步转移很简单，中间结果却能写回「纸带」，供下一步继续计算。一次很浅，串起来就有了深度。

6.2 用 Token 换计算深度#

这样，更多 token 就可能换来更多计算深度（test-time scaling）。它是否有效，取决于模型有没有找到能推进问题的步骤，以及能不能识别错误。

  • 你可以同时提很多要求，AI 会想出像人一样逐步逼近目标的过程：test-time scaling。
  • 「找解常常比验解难」适合作为 P vs. NP 的直觉类比，不是复杂性证明。只有当中间进展或最终答案可检查时，多写、多试、多修补才会稳定地变成能力。

7. 三道刁难人的写作题：指令遵循的压力测试#

为了把指令遵循的难度具体摆出来，课堂给了几道故意刁难人的写作题。（幻灯片 17–20）

7.1 三条约束，藏进八句诗#

题目用中文写一个押韵的藏头诗，头是「计算机学院真牛逼」，要讲和动物相关的故事，「二零二六九月一日」八个字分别按顺序出现在八句里，位置无所谓。
生成素材

计成二兔越山冈
算到零时雪满塘
机警狐衔二袋粮
学随六雁辨风向
院中九犬忽声扬
真到月明逢恶狼
牛守一夜迎晨光
逼得日升狼遁荒

  • 竖读句首：计算机学院真牛逼。
  • 逐句取指定字：二零二六九月一日；八句同押 ang 韵。
  • 这像三条并行信道：句首放藏头，句中放日期，句尾管押韵；先占槽位，再「生成—检查—修补」。

检查时，可以先竖读句首，再逐句寻找指定字，最后看句尾和故事。藏头与嵌字都能对上，句尾也有相近的韵感，但「方向」的「向」与其他句尾在普通话拼音中并不完全相同，读起来有些句子也明显是为了凑约束。它展示的是模型能够寻找并修补一个多约束解，而不是宣告模型已经写出好诗。

7.2 十八个字，一片水#

题目写十八字的一句话，全部有相同的偏旁或部首，要有实际意义和故事性。
生成素材

洪涝淹没江港渔浦，油污漂浮，沈涛泅渡济溺。

  • 不计标点恰好 18 字，每个字都带「氵」。
  • 灾害、地点、污染、人名、动作和结果都从同一语义场里长出来；约束缩小了搜索空间，也把常用虚词几乎全挡在门外。
  • 「偏旁」是字形构件，「部首」主要是检字分类。若要机械验收，spec 应写成「18 个汉字都含同一可见偏旁」。

这里的检查比较直接，但「都含三点水」和「词典中都归为同一部首」仍然是不同要求。要交给程序验收，就得先决定检查的是哪一个——验收口径本身就是 spec。

7.3 只许一个音，还要讲现代故事#

题目写一大段话（文言文），要求全部同一个音，也要有实际的故事性，不能用《施氏食狮史》和《季姬击鸡记》原文，原创一个有现代背景的。
生成素材（Yi 音文）

乙易一译仪。仪译异义，乙疑，诣驿议易。驿役揖乙，亦疑仪已异，移仪以医。翌，仪已宜，译义亦宜，乙怡。乙以仪译异裔意，异裔亦怡；乙益以译艺，逸矣。

  • 所有汉字的拼音音节都是 yi，声调可以不同：有人买了翻译器，发现误译，去快递驿站换修，翌日取回后终于正常。
  • 「同音」是否包含声调，会让难度骤变；验收口径本身就是 spec。文字尚可借字形消歧，朗读出来几乎不可懂。

7.4 通过测试，不等于写得好#

这三道题把两类评价放在了一起：Verifier 看得见的与Verifier 看不见的。

Verifier 看得见的：

  • 藏头、嵌字顺序、字数、偏旁、拼音，都可以写成检查器。
  • 模型不必一口气「灵感命中」：它可以先找可行解，再逐条验证，发现违约就追加 token 修补。
  • 约束文学早有类似实验：乔治·佩雷克 1969 年的小说《消失》全书避用法语字母 e。形式约束能逼出搜索，却不会自动带来好作品。

Verifier 看不见的：通顺、趣味和文学性需要更丰富的判断。以上其实已经超越大部分人类的极限了——模型作为「人类」的推理能力真的很强，虽然品味还可以提高。

通过检查器，说明它会搜索和修补；读起来仍有点别扭，说明测试没有覆盖品味。

模型通过形式检查，说明它能够搜索和纠错，但形式检查没有覆盖的质量，并不会自动出现。软件测试也有类似的边界。

8. 上下文中的规则，也会争夺注意力#

8.1 过去的上下文一直都在场#

把要求写进上下文，可以让模型在生成过程中反复利用它（幻灯片 21）。

  • 每一个 token 的输出都会「注意」到过去的上下文。
  • 全局的 AGENTS.md 里要求用中文，这个「用中文」会一直保持一定的注意力。
  • 全局的 git commit 不要「Copiloted by Claude Code」。
  • 每一个 token 都会看到这些；适当的时候，下一个 chain-of-thought 就会纠正错误。

模型每输出一个 token，就又多了一次发现偏航、把轨迹拉回来的机会。但「看得见」不是硬约束——Lost in the Middle 也提醒我们，长上下文中的信息并不会被同样可靠地利用。

8.2 提示词的副作用：要求变成注释#

提示词还会带来副作用（幻灯片 22）。你说「白色背景，不要半透明效果」，模型可能把这句话变成代码里的注释：

实际输出... // 白色背景（不要半透明效果）😂

它完成了背景设置，却也把原本只用于沟通的要求带进了产物。

否定指令有个尴尬之处：为了禁止「半透明」，你先把「半透明」写进了上下文。这和「不要想白熊」有相似的反直觉味道，但对模型来说，直接原因更朴素：被禁止的词也成了可续写的模式。

8.3 常驻，还是按需加载？#

于是，一个看似合理的修补办法出现了：再加一条永久规则，禁止把用户要求写进注释。但每遇到一次问题就增加一条规则，上下文会越来越长，约束之间也越来越难协调。这不是免费的增强。

更合适的做法，是区分长期适用的简短规则与当前任务需要的细节：

  • 常驻层只放「每次都要守、漏一次代价很高」的短规则；任务细节按需加载。
  • 能写成检查项的，就用 background: #fff; opacity: 1 这类正规格和测试收口——白色背景可以由具体样式和渲染结果确认，不必依靠越来越长的自然语言劝诫。

上下文工程因此也包含取舍：删去一段无关说明，有时和增加一条关键要求同样有效。模型需要的不是尽可能多的文字，而是此刻做决定时用得上的信息。

9. 「你是一位审稿人」，还不够#

课堂接着把任务换成论文审稿：假装自己是 ICSE 的审稿人，阅读指定论文，写一份约一千英文词的 review，并判断是否应该接收。（幻灯片 23–26）

9.1 AI 耿同学上线#

这次用的是老师自己的 paper：

Prompt假装作为 ICSE'27 的审稿人 icse27-901.pdf，我应该接收它吗？写一个 1000 words 左右的 Review.txt。

模型很容易写出一份看起来像审稿意见的文本：总结贡献，列出优点和不足，再给出一个建议。问题是，它究竟完成了多少判断？

「你是 ICSE reviewer」主要改变的是先验、语气和输出形状；它不会凭空补上审稿标准、证据链和反证程序。换上 reviewer 的制服，不等于学会了 review。

9.2 怎样构造一个好的 Reviewer：三条独立路线#

可以把审稿工作拆成三条不同的路线：

路线做法
判据驱动先还原论文声称的贡献，再按审稿标准独立打分；每个分数都必须指向论文中的证据或明确的缺失。
证据审计为每个核心 claim 建账本：它需要什么证据、论文给了什么、哪些假设没验证、还有什么替代解释。
反方复现站在最强反方或复现者的位置，重算一个核心结果，寻找最小反例，并问「什么观察会推翻结论？」

这几条路线的价值来自问题不同。若一开始就共享同一个总体印象，最后可能只得到同一个判断的三份润色。因此——三条路线先各自形成判断，最后才汇合。否则「三个 reviewer」很容易只是同一个锚点的三次润色。独立形成初步意见，再比较分歧，才更容易发现原先没有看到的东西。

这也说明人的方法论如何影响 AI 的结果。你不必替它读完每一行，但需要知道什么算有根据的判断、哪些证据缺失值得追问。短程任务里，把方向带对、把标准说清楚，往往已经能显著改变产物。

9.3 不要被作者「带着走」#

方法论决定 AI 的上限。（幻灯片 25）

  • 短程任务，基本上带对方向、明确指令就可以了；但你的方法论（品味）决定了 AI 的上限。
  • 文章的信息密度非常大，相当于极度吸收注意力。
  • 你的一些 critical thinking、first-principle thinking，都可能架不住被论文作者本身的逻辑带着走。
  • 论文不只提供事实，还替 reviewer 选择了词汇、问题顺序、baseline 和 metric。等你开始判断作者的答案时，作者可能已经替你筛掉了更关键的问题；这正是锚定效应危险的地方。

论文的信息密度非常高，作者不仅给出了答案，也替读者选好了问题、术语、比较对象和衡量标准。如果顺着文章走完一遍才开始评价，很容易在不知不觉中接受了作者的整个框架——你以为自己在批判性思考，其实只是在作者划好的场地里打转。

深读前先独立写下三件事：它声称解决什么、最强替代解释是什么、什么结果会推翻它；再把正文拆成 claim → evidence → assumption。空格往往比句子更值得审。

9.4 把品味蒸馏成 Skill#

从偶然成功到可重复的方法。（幻灯片 26）

当一套做法多次有效，就可以把它沉淀成 skill。Skill 看起来是一段提示词，真正值得保存的，是成功经验中的搜索策略、判断标准、检查点，以及「看到什么证据就转向」的条件。它帮助 Agent 复用一种做事的方法，而不是每次重新凭第一印象发挥。

Skill 本身也是一道遵循题。

  • Caveat：长 Skill 里有大量指令，会提升指令遵循的难度；在 AI 看来，和写藏头诗可能差不多 😂
  • 把 Skill 分层：常驻层只留目标、硬约束和停止条件；解释、范例、边界案例按需加载；机械约束交给工具验证。
  • 少写一句劝诫，多加一个可检查的完成条件。

如果把所有想得到的要求都塞进去，Skill 本身就会变成一道复杂的指令遵循题，和前面的藏头诗颇有相似之处。保留真正影响决策的内容，把机械工作交给脚本，把需要时才看的材料单独放置，才能让经验更容易复用。

10. 为什么大仓库有时比空项目更容易#

课堂提出了一个有趣的观察：从零做一个看起来不难的产品，AI 可能在某个时间点开始不断翻车；进入一个成熟的大型系统，反而能够完成相当复杂的修改。（幻灯片 27–30）

10.1 Long-Horizon 能力是怎么「练」出来的#

模型是训练出来的。只要有反馈信号，就可以强化学习：答对了给奖励，答错了揍。后训练逼迫模型规划、思考，学会非常离谱的长程代码能力，能不断试错、解决问题，直到满足要求；连刚才那些折磨人的「语文」指令也顺便学会了。

  • Long-horizon 不是一次性想得特别深，而是闭环控制：尝试 → 编译 / 测试 → 观察 → 修复。真正变长的是「出错以后还能回来」。
  • 代码世界格外适合这件事：构建、测试、benchmark 都能反复给出便宜的判分信号，很像 AlphaGo Zero 拥有规则确定、结果可验证的棋盘。（Nature, 2017）

反馈也可能教坏模型：如果测试只覆盖表面行为，「坚持」也可能变成 reward hacking——不是逼近你的真实目标，而是把公开分数刷满。因此还需要 held-out tests 和独立 review。

10.2 Greenfield 悖论：大型系统反而更容易？#

从零开始做产品看起来不难，AI 却会从某个时间点开始各种翻车。反而在大型复杂软件系统里，AI 游刃有余，令人迅速滑跪？

  • self-attention 可以「看到」好的 practice，并且立即 in-context learn，学到应该遵循的已有 best practice。
  • 如果产品起步时没有建立良好的工程纪律，AI 会学会在 slop 上无限叠加。
  • 启发：「提示词」不仅是你输入的，甚至代码库本身也是「提示词」。

代码少，不代表信息少。

  • 成熟仓库用命名、分层、错误处理和测试，把巨大的设计空间压成「照着邻居补全」；greenfield 里每个选择都悬空，信息熵反而更高。
  • 模型只会追求局部一致性，并不知道眼前的是 best practice 还是历史事故。第一桶 slop 一旦成为多数派，后面的 slop 会像复利一样增长。

可以从上下文的角度理解这种差别。成熟代码库已经做出了许多决定：怎样命名，模块如何分层，错误怎样传播，测试放在哪里。Agent 在解决局部问题时，可以学习附近的例子，沿着现有结构补充实现。代码量虽然大，当前任务需要自由选择的事情却可能更少。

10.3 「放一个好项目给 AI 看」靠谱吗？#

课堂提出了一个未经实验验证的猜测：在代码库里放一个相近领域、优雅成熟的高质量系统，先让 AI 读一下，再实现需求，能得到质量更高的软件。调研结论：猜测成立一半。

  • 机制上合理，但「相近、精选、按需取用」比「整个仓库塞进去」重要。
  • RepoCoder 中，迭代检索仓库相关片段比只看当前文件的 baseline 提升超过 10%；这支持「好示例有用」，却没有证明外来大仓库必然有益。
  • CodeRAG-Bench 的结论更克制：高质量 context 会帮忙，但「找对片段」和「真的用好片段」仍是瓶颈。
  • 整库输入还可能带来 negative transfer：技术栈、约束、依赖或架构哲学不匹配；它也会消耗 context，让真正相关的约束被淹没。

一个能做的对照实验：固定任务、模型、token budget 和随机种子，对比「无示例 / 完整参考仓库 / 3–5 个精选 golden paths」。除了通过率，还要盲测架构违规、修改扩散面、review 时间、后续缺陷和代码克隆率。预测：精选的端到端竖切片最稳。

这个猜测值得做实验，但还不是结论：相近领域到底有多相近？应该读整个项目，还是几个关键例子？如果参考项目的约束与当前任务不同，会不会把不合适的架构也学过来？

10.4 没有「超能力 AI」：你仍然需要「有概念」#

对你要实现的东西有概念，现在仍然非常重要。这只能通过学习获得。课程会用一学期来解释如何用软件工程的方法：给出正确指令、监控 AI 运行、防止 AI 失控……

  • 对 CS 学生来说，学科知识体系仍然非常重要：处理器、操作系统、编译器、数据库里有很多设计智慧。
  • 你需要把模型引导到你认为合适的位置上。
  • 但你不理解的东西是不能驾驭的。

学习的目标变了。领域知识不是为了和 AI 比每分钟写多少行，而是给出不变量、接口边界和失败模式：什么时候「能跑」仍然是错的。

Bainbridge 在 1983 年就指出「自动化的反讽」：容易的部分被自动化，人留下的恰好是异常、接管和无法预演的情况，因此反而需要更深的系统模型。（Ironies of Automation）

理解接口、不变量、状态和失败模式，才能知道该把模型引向哪里。对所做的东西「有概念」，仍然是驾驭它的前提。只是现在，学到一个原理以后，可以更快地把它用到真正的系统里。

11. Research Failure：Token 花完了，知识没有增加#

11.1 符号执行引擎优化#

能够执行长程编程任务，意味着模型在遇到错误后仍能继续：修改、构建、测试、观察，再修复。这样的闭环依赖反馈。测试失败提供了具体方向，编译器报错指出了局部问题，模型可以据此不断尝试。

但把任务交给更强的模型、投入更多 token，并不保证任何长程问题都会收敛。课堂讲了一个研究失败案例：

试图优化一个符号执行引擎：有一个原始 idea，问题带一点 active、open-ended research 的味道，但也只是希望往前推进一点点。

PhD student：GPT-5.6 Sol Ultra 启动！benchmark 丢进去，想法丢进去，花了很多 token，没有结果。

原稿没有给出已经查明的失败原因，因此这里能做的是提出待检验的解释。

11.2 问题可能出在哪？#

  • 缺的不是 token，而是便宜、局部、可归因的反馈。一个总 benchmark 分数几乎不给下一步方向。
  • 「没变快」可能来自 path explosion、solver、缓存、内存、搜索策略、实现 bug 或环境噪声；Agent 不知道该强化哪一步。
  • 更要命的是：Agent 被训练成「把任务做完」，研究却允许最好的结论是「原始 idea 不成立」。没有可证伪假设，它可能把错误想法实现得越来越完整。
  • 经典的 KLEE 把问题拆成搜索策略、约束缓存、independent constraint sets 等机制，再分别测量。
  • 更合理的起点：先 profile 主导瓶颈，把 idea 改写成一句可证伪预测，造几十秒就有反馈的 microbenchmark，再做 baseline 和 ablation。

一个可能的问题，是总 benchmark 分数提供的反馈太粗。没有变快，究竟是主要时间花在求解器里，路径搜索策略有问题，缓存没有起作用，还是修改引入了新的开销？如果这些因素混在一起，下一步应该试什么就很难判断。另一个可能的问题，是任务把「把这个想法实现好」当成了目标，但研究真正需要回答的，可能是「这个想法是否成立」。

因此，更有用的起点可能是先测量主要瓶颈，把想法写成一个可以被实验推翻的预测，再构造能够快速反馈的小实验。确认局部机制确实有效以后，才把它放回完整系统，检查收益是否仍然存在。研究中的「推进」可以是缩小未知，也可以是排除一个方向；不能只把它定义成最终分数必须上涨。

12. 人应该盯住哪些地方#

既然人了解领域，随时干预是否最好？（幻灯片 32–33）

12.1 少干预，反而做得更多#

课堂给出的经验恰好有点反直觉：我知道怎样让某个任务更快完成，却越来越少干预了。

Latency 和 Throughput 是两回事。

  • 人类干预优化单个任务的 latency；放手让 Agent 跑，优化的是一整天的 throughput。机器多走一点弯路，换回最稀缺的人类注意力。
  • 放手成立有两个前提：任务可以并行，失败可以便宜地恢复。否则「少干预」只是把故障推迟。

原因在于，单个任务的完成时间与一天能完成的任务总量，是两个不同目标。如果 Agent 走一点弯路最后也能完成，我可以把注意力移到另一件事上。机器多花一些时间，换回人的时间，整体产出反而增加。

12.2 Review 什么？#

这种取舍需要有边界。按「不可逆性 × 爆炸半径」分配注意力：接口、不变量、数据格式、权限和测试早看；可替换的叶子实现可以晚看。

  • 比如接口我 review 过了，实现是 AI slop，最后出问题了修就行 😂
  • 相反，一个会扩散到许多模块的接口决定，一个昂贵或难以恢复的动作，就更值得提前关注。
  • 丰田的「自働化」也是这个逻辑：一个人照看多台机器，靠异常自动停机和 andon 报警，而不是盯住每一步。Agent 的对应物是 CI、预算、权限边界和 stop condition。

人的注意力应当按照决策影响和返工代价分配，而不是平均撒在每一行代码上。

12.3 Context 越长，不等于记得越牢#

长任务还会不断产生日志、补丁和工具输出。上下文能容纳这些材料，不代表模型在每个时刻都能同样有效地使用它们。

  • 随着上下文增长，指令遵循会下降；但最后的 prompt、刚加载的 skill 通常仍能遵循，因此干活还是很好用的。
  • Context window 是容量，不是有效注意力。日志、补丁和工具输出不断进入工作集后，「还在窗口里」不等于「此刻用得上」。
  • Lost in the Middle 发现，相关信息放在长上下文中部时，模型往往不如放在开头或结尾时用得稳定；这也解释了末尾 prompt 和新加载 skill 的优势。

课堂观察到，随着上下文增长，指令遵循可能下降，而最近的要求或刚加载的方法往往更容易被执行。具体表现取决于模型和任务，但工程上可以主动缩短关键要求到关键决定之间的距离。

12.4 把要求从「记忆」升级成「机制」#

  • 关键要求在决策点重新落地：短 checklist、阶段性重读 spec / skill、合并前复述不变量。
  • 能编码成类型、lint、property tests、CI gate 和权限沙箱的，就别只写在 prompt 里。prompt 会被压缩，失败的测试不会假装自己通过。
  • 上下文压缩应保存「目标、约束、未决问题、证据」，而不是按时间线复述发生过什么。

例如，在阶段切换时重新确认目标、接口和未决问题；把能检查的不变量落实成测试；让错误在继续传播之前暴露。这样，人的放手才有可以依靠的反馈机制。

13. 在不确定性中探索#

到这里，我们一直在讨论怎样把任务说清楚。但许多有价值的任务，本来就没有确定路线。我们希望 AI 帮助探索，而不仅仅执行已经写好的计划。（幻灯片 34–37）

13.1 这次不是「解题」#

我就是希望模型在不确定性中探索。

  • 如果所有要求和路线都想清楚了，这就是一个相对无趣的问题：Chain-of-thought 就能解决。
  • 今天「帮我考虑一下几种方案」有效，但可能不是最佳的。
  • 模型被训练成了「完成任务」才有奖励，所以它会给你有限的方案；complexity gap 里，那个「更好」的可能被藏起来了。

13.2 谁规定「已经想完了」？#

  • 「给我几种」只规定了停止条件 k，没有规定覆盖率。这正是 Herbert Simon 所说的满意化（satisficing）：搜到「够好」就停。
  • CoT 用算力换深度：沿一条路多走几步；并行枚举用算力换宽度：让更多轨迹进入低概率的尾部。

探索的瓶颈常常不是「想不出」，而是模型太早认定「已经够了」。

「帮我考虑几种方案」通常有效，却可能过早结束。模型给出几个听起来合理的答案，已经满足了「几种」的数量要求；更有意思的方案，也许仍在它没有走到的方向里。此时，多沿一条思路想一会儿，与主动探索更多不同思路，是两种不同的算力使用方式。

13.3 算力换智力：把灵感改造成搜索#

方法：test-time scaling 的另一个维度。课堂用取名字作例子：给一个蒋姓的小孩取好听、又有寄托的名字。

不要只问「给我几个名字」：直接让它给一些，AI 有自己的 bias；你可能不太想用——别人也会用，成为 AI 时代的 zǐhán（「子涵」）。

把灵感改造成搜索：

  • 定义探索空间、要求枚举、sub-agent 检查。
  • 生成：典故 × 音韵 × 方言 × 时代感；先独立采样，再汇总，别让 sub-agent 一开始就互相抄答案。
  • 审名：查出处、听谐音、看重名，再让「反对者」专挑毛病。

枚举负责提高覆盖率，审查负责提高分辨率：选择质量 ≈ 覆盖率 × 评估分辨率

这里仍然离不开人的判断。「给更多名字」解决的是候选数量，「哪些名字值得留下」则需要评价标准。没有分辨率的筛选，可能只是把一个平庸答案变成一百个平庸答案。探索空间与评价方法应当一起设计。

13.4 我们一直在「多采样」：世界很大，人很小#

  • 人的品味来源于 diversity：不同的教育背景、生活圈、经历……（Richard Sutton's Big World Hypothesis）
  • 人天生对所有问题都有 bias；但 1 + 1 > 2：无论是和舍友菜鸡互啄，还是去开 conference，都是在理解对方的 bias，促进群体智能，然后每个人继续带着 bias 创新。

群体智能不要求每个人没有偏见；它只要求偏见不能只剩一种。交流也不是尽快共识，而是先让不同误差活下来。

人类社会其实一直在通过类似方式扩展自己的视野。每个人的教育背景、生活圈和经历都有限，也都带着偏向。与舍友讨论，去会议上听别人怎样提出问题，价值往往来自发现自己的默认前提。交流之后，每个人仍有自己的偏向，但它已经被新的经验改变。

课堂借「世界很大，人很小」的视角提醒我们，没有人能独自穷尽所有可能。群体的价值可以来自不同的局限相互补充。把这个思想带回 Agent：增加计算资源时，应当考虑怎样增加探索的差异，而不是只增加同一种思路的重复次数。

13.5 墙内的超人#

如果计算资源能够持续转化为探索能力和判断能力，这也带来了一个令人不安的未来问题。

算力成为生产资料。这也是未来可能发生、非常残酷的现实：资本家可以获得无限的计算资源，获得无限的智力，「人」本身的价值在减弱——砌一堵墙，墙里面是超人，墙外面是动物世界。

  • Stanford AI Index 2025：2024 年近 90% 的 notable models 来自产业界；若干前沿模型的训练算力成本已经是数千万到近两亿美元。

这是对未来可能性的追问，并非已经发生的终局。

对于正在学习的我们，可以从眼前开始改变做事方式：让模糊愿望获得可检查的表达，把有效经验沉淀成可复用的方法，在需要探索时主动扩展方向，又用证据筛选结果。提示词的价值，最终要落在这些行动如何改变任务的结果上。

14. 术语表#

Prompt / 提示词
给模型的输入文本。从续写角度看，它是控制后续生成的条件；对 Agent 来说，它分散在 system prompt、AGENTS.md、skill、用户指令与工具返回等处。
Context / 上下文
模型做下一步决策时能看到的全部 token，包含指令、材料、证据与过程记录。Pr[token | context] 中的 context 即此。
Harness
运行 Agent 的外围系统：提供系统指令与工具说明，并负责权限检查、审批规则等外部机制。
AGENTS.md
仓库中的持久指令文件，约定项目规则、语言和格式等长期约定。
Skill
可复用的做事方法。值得保存的是搜索策略、判断标准、检查点，以及「看到什么证据就转向」的条件，而不只是答案版式。
上下文工程（Context Engineering）
关心每次决策前，哪些 token 以什么来源、顺序和作用域出现；目标是让 working set 足够小、足够新、带来源、可验证。
Intent / Spec / Impl
意图（想要什么）→ 规格（可检查的判据）→ 实现（代码）。三者之间的缺口会逐级放大漂移。
Gap
Intent 与 Impl 之间被省略、由模型用默认值补全的选择空间。
Chain-of-Thought（CoT）
把中间结果写回上下文、逐步逼近目标的生成方式；用算力换深度。
Test-time scaling
在推理时投入更多计算（更多 token、更多试错、更多轨迹）来提升结果质量。
Verifier / 验收器
判定「完成」的检查程序或证据。人定义目标 G 与验收器 V，AI 搜索实现 x，直到 V(x)=1。
停机条件（done）
上下文里可识别的完成判据 V(τ)=1；没有它，「继续干」和「可以交卷」只是两种高概率续写。
满意化（Satisficing）
Herbert Simon 的概念：搜到「够好」就停。「给我几种」只规定 k，不规定覆盖率。
AI slop
低质量、应付式的生成产物；若第一桶 slop 成为多数派，后续 slop 会像复利一样叠加。
Greenfield 悖论
空项目反而更容易翻车、大仓库反而游刃有余的现象。
In-context learning
模型在上下文中即时学习示例与既有 practice 的能力（依赖 self-attention）。
Reward hacking
把公开分数刷满，而不是逼近真实目标；需要 held-out tests 与独立 review 制衡。
Lost in the Middle
长上下文中部信息不如开头/结尾被稳定利用的现象。
Essence / Accident（Brooks）
软件的本质困难（构造、规格化、设计、测试概念结构）与偶然困难（表示成代码）。No Silver Bullet, 1986。
Negative transfer
参考项目的技术栈、约束或架构哲学不匹配，反而拉低表现。
Golden paths
从参考仓库中精选的端到端竖切片示例，比整库输入更稳。
Latency / Throughput
单任务完成时间 vs 一天能完成的任务总量。人干预优化 latency，放手优化 throughput。
自働化（Jidoka）/ Andon
丰田生产系统的思想：异常自动停机 + 报警，一个人照看多台机器。Agent 的对应物是 CI、预算、权限边界与 stop condition。
Context window
上下文容量，不等于有效注意力。
Self-explanation / Retrieval practice
费曼学习法飞轮的实证支点：用自己的话重述 + 检索式练习。
Ironies of Automation
Bainbridge, 1983：容易的部分被自动化，人留下的恰是异常与接管，因此需要更深的系统模型。
Sandbox / Approval policy
决定技术上能碰什么、何时暂停询问的外部机制。安全属性属于完整 invocation，而非命令名（CVE-2025-54558）。
Big World Hypothesis
Richard Sutton：世界很大，个体很小；群体的价值来自不同 bias 的相互补充。

Slide 8立即行动：解剖当前上下文

让 Agent 解释“谁在给它下指令”

分析一下你上文中的所有提示词 (包括系统)，并按照需要遵循的指令类型分类总结。

Slide 10上下文工程：让模型知道“完成”是什么

Context 里是一份复杂要求

  • 模型的潜力完全是靠提示词激发的
  • 上下文包含了一个极为复杂的要求
    • 约束，可以是 intent，也可以是 spec
  • 模型被训练为：持续的 Pr[token | context] 能不断推进，直到满足要求，也就是学会了“规划”的能力

逐 Token 推进，也要有停机条件

  • Pr[token | context] 本身不是规划器；后训练把多步试探、工具调用和收尾塑造成了一种可采样的策略。
  • 设生成轨迹为 τ。只有上下文里存在可识别的完成判据 V(τ)=1，“继续干”和“可以交卷”才不只是两种高概率续写。

Slide 11可验证，才不会“提前交卷”

模型如何判断已经满足？

  • 推论：越明确、越可验证的要求，越可能得到你满意的结果
  • 不明确的要求，模型可能认为已经“满足”了
  • 一个直接的检查：旁观者只看产物和工具结果，能否判定通过或不通过？如果不能，模型就没有稳定的 done。

Slide 13写清指令，承担“不明确”的后果

Rule of Thumb

  • 写清楚你的指令，承担一切“不明确”的后果
    • 这样模型永远给你的是惊喜 😁
  • 授权模型用默认值替你做产品决策。
  • 1854 年轻骑兵冲锋中，山上的 Raglan 看得见目标，谷中的 Lucan 看不见；命令里的“那些炮”由执行者自行补全，轻骑兵最终冲向了错误的炮阵。英国国家陆军博物馆：原始命令

要么完成，要么显式失败

  • 一个足够好的模型，要么完成，要么失败，不应该幻觉或违背指令

  • 可以把失败语义写进契约：只有测试或可检查证据通过才算完成；无法验证时，报告未完成、阻塞点和已经尝试的路径。

Slide 14从“AI 味”到你的主页

Bad：把品味留给默认值

“我是蒋炎岩，根据我的公开信息，制作一个现代风格的个人主页首页...” 你将会得到 AI 味

“现代风格”看似具体，实际上几乎没有排除任何模板。两个称职的实现者都能严格照做，却交出完全不同的页面：这仍然只是 intent。

Better：压缩合法解空间

...，用具体风格、具体样式和排版... 就可以得到我的个人主页

颜色、字体、栅格、留白、组件和参考物共同构成设计语言。关键不是多写几个形容词，而是让选择可组合、结果可检查。

Impl 变便宜，判断没有

Slide 16一步很浅，一串可以很深

Pr[token | context]

Pr[token | context] 是深度非常有限的计算。即使是今天的 Mixture-of-Experts，所谓“专家”也只是表示空间上的分段函数，并不是坐在模型里的多个小人。大部分时候，接下来若干个“简单” token 都是高概率确定的；一次前向计算不可能凭空完成复杂任务。

但模型学会了利用上下文思考：遇到不确定之处，不直接猜答案，而是先试一试；错了，还可以继续输出 token 纠正。每个新 token 又成为下一步的 context，这就是 chain-of-thought。

可以把它类比成图灵机的纸带：单步转移很简单，中间结果却能写回“纸带”，供下一步继续计算。一次很浅，串起来就有了深度。

用 Token 换计算深度

  • 你可以同时提很多要求，AI 会想出像人一样逐步逼近目标的过程：test-time scaling。
  • “找解比验解难”适合作为 P vs. NP 的直觉类比，不是复杂性证明。只有当中间进展或最终答案可检查时，多写、多试、多修补才会稳定地变成能力。

Slide 17三条约束，藏进八句诗

用中文写一个押韵的藏头诗，头是“计算机学院真牛逼”，要讲和动物相关的故事，“二零二六九月一日”八个字分别按顺序出现在八句里，位置无所谓。

计成二兔越山冈
算到零时雪满塘
机警狐衔二袋粮

真到月明逢恶狼

  • 竖读句首：计算机学院真牛逼。

Slide 18十八个字，一片水

同一偏旁，还得有故事

写十八字的一句话，全部有相同的偏旁或部首，要有实际意义和故事性。

洪涝淹没江港渔浦，油污漂浮，沈涛泅渡济溺。

  • 不计标点恰好 18 字，每个字都带 氵。
  • 灾害、地点、污染、人名、动作和结果都从同一语义场里长出来；约束缩小了搜索空间，也把常用虚词几乎全挡在门外。
  • “偏旁”是字形构件，“部首”主要是检字分类。若要机械验收，spec 应写成“18 个汉字都含同一可见偏旁”。

Slide 19只许一个音，还要讲现代故事

原创 Yi 音文

写一大段话（文言文），要求全部同一个音，也要有实际的故事性，不能用《施氏食狮史》和《季姬击鸡记》原文，原创一个有现代背景的。

乙易一译仪。仪译异义，乙疑，诣驿议易。驿役揖乙，亦疑仪已异，移仪以医。翌，仪已宜，译义亦宜，乙怡。乙以仪译异裔意，异裔亦怡；乙益以译艺，逸矣。

  • 所有汉字的拼音音节都是 yi，声调可以不同：有人买了翻译器，发现误译，去快递驿站换修，翌日取回后终于正常。
  • “同音”是否包含声调，会让难度骤变；验收口径本身就是 spec。文字尚可借字形消歧，朗读出来几乎不可懂。

Slide 20通过测试，不等于写得好

Verifier 看得见的

  • 藏头、嵌字顺序、字数、偏旁、拼音，都可以写成检查器。
  • 模型不必一口气“灵感命中”：它可以先找可行解，再逐条验证，发现违约就追加 token 修补。
  • 约束文学早有类似实验：乔治·佩雷克 1969 年的小说《消失》全书避用法语字母 e。形式约束能逼出搜索，却不会自动带来好作品。

Verifier 看不见的

以上已经超越大部分人类的极限了。模型作为“人类”的推理能力真的很强，虽然品味还可以提高。

通过检查器，说明它会搜索和修补；读起来仍有点别扭，说明测试没有覆盖品味。

Slide 21用好模型遵循指令的能力

过去的上下文一直都在场

  • 每一个 token 的输出都会“注意”到过去的上下文
  • 全局的 AGENTS.md 里要求用中文，这个“用中文”会一直保持一定的注意力
  • 全局的 git commit 不要 “Copiloted by Claude Code”
  • 每一个 token 都会看到这些；适当的时候，下一个 chain-of-thought 就会纠正错误
  • 模型每输出一个 token，就又多了一次发现偏航、把轨迹拉回来的机会。但“看得见”不是硬约束；Lost in the Middle 也提醒我们，长上下文中的信息并不会被同样可靠地利用。

Slide 22上下文也是争用资源

规则会纠偏，也会抢注意力

  • 副作用：提示词会抢夺注意力
  • 人：要白色背景，不要半透明效果
  • AI：... // 白色背景 (不要半透明效果) 😂
  • 否定指令有个尴尬之处：为了禁止“半透明”，你先把“半透明”写进了上下文。这和 “不要想白熊” 有相似的反直觉味道，但对模型来说，直接原因更朴素：被禁止的词也成了可续写的模式。

常驻，还是按需加载？

  • 两难问题：要不要用一个常驻 AGENTS.md prompt 把这种行为压下去，但同时污染上下文？
  • 常驻层只放“每次都要守、漏一次代价很高”的短规则；任务细节按需加载。能写成检查项的，就用 background: #fff; opacity: 1 这类正规格和测试收口。

Slide 23AI 耿同学上线！

这次用的是我自己的 paper

假装作为 ICSE'27 的审稿人 icse27-901.pdf，我应该接收它吗？写一个 1000 words 左右的 Review.txt。

那我会怎么读一篇 paper 呢？我的日常阅读流程，例如 arXiv，是怎样的？

“你是 ICSE reviewer”主要改变的是先验、语气和输出形状；它不会凭空补上审稿标准、证据链和反证程序。换上 reviewer 的制服，不等于学会了 review。

Slide 24怎样构造一个好的 Reviewer？

三条独立的审稿路线

  • 判据驱动：先还原论文声称的贡献，再按审稿标准独立打分；每个分数都必须指向论文中的证据或明确的缺失。
  • 证据审计：为每个核心 claim 建账本：它需要什么证据、论文给了什么、哪些假设没验证、还有什么替代解释。
  • 反方复现：站在最强反方或复现者的位置，重算一个核心结果，寻找最小反例，并问“什么观察会推翻结论？”

三条路线先各自形成判断，最后才汇合。否则“三个 reviewer”很容易只是同一个锚点的三次润色。

Slide 25不要被作者“带着走”

方法论决定 AI 的上限

  • 短程任务，基本上带对方向、明确指令就可以了；但你的方法论（品味）决定了 AI 的上限
  • 文章的信息密度非常大，相当于极度吸收注意力
  • 你的一些 critical thinking、first-principle thinking，都可能架不住被论文作者本身的逻辑带着走
  • 论文不只提供事实，还替 reviewer 选择了词汇、问题顺序、baseline 和 metric。等你开始判断作者的答案时，作者可能已经替你筛掉了更关键的问题；这正是锚定效应危险的地方。
  • 深读前先独立写下三件事：它声称解决什么，最强替代解释是什么，什么结果会推翻它；再把正文拆成 claim → evidence → assumption。空格往往比句子更值得审。

Slide 26把品味蒸馏成 Skill

从偶然成功到可重复的方法

当你有成功的经验，就可以蒸馏成 Skill：看起来只是个 prompt，其实是用可复用的方式约束模型的行为和方向。现在的模型还没到“第一感觉就打遍天下无敌手”的状态，尤其是答案不唯一的时候。

  • 好的 Skill 保存的不是上次答案的版式，而是搜索策略、判断标准、检查点，以及“看到什么证据就转向”的条件。

Skill 本身也是一道遵循题

  • Caveat：长 Skill 里有大量指令，会提升指令遵循的难度；在 AI 看来，和写藏头诗可能差不多 😂
  • 把 Skill 分层：常驻层只留目标、硬约束和停止条件；解释、范例、边界案例按需加载；机械约束交给工具验证。少写一句劝诫，多加一个可检查的完成条件。

Slide 27Long-Horizon 能力是怎么“练”出来的？

模型是训练出来的

只要有反馈信号，就可以强化学习：答对了给奖励，答错了揍。后训练逼迫模型规划、思考，学会非常离谱的长程代码能力，能不断试错、解决问题，直到满足要求；连刚才那些折磨人的“语文”指令也顺便学会了。

  • Long-horizon 不是一次性想得特别深，而是闭环控制：尝试 → 编译/测试 → 观察 → 修复。真正变长的是“出错以后还能回来”。
  • 代码世界格外适合这件事：构建、测试、benchmark 都能反复给出便宜的判分信号，很像 AlphaGo Zero 拥有规则确定、结果可验证的棋盘。(Nature, 2017)

反馈也可能教坏模型

  • 如果测试只覆盖表面行为，“坚持”也可能变成 reward hacking：不是逼近你的真实目标，而是把公开分数刷满。因此还需要 held-out tests 和独立 review。

Slide 28大型系统，反而更容易？

Greenfield 悖论

从零开始做产品看起来不难，AI 却会从某个时间点开始各种翻车。反而在大型复杂软件系统里，AI 游刃有余，令人迅速滑跪？

  • self-attention 可以“看到”好的 practice，并且立即 in-context learn，学到应该遵循的已有 best practice。
  • 如果产品起步时没有建立良好的工程纪律，AI 会学会在 slop 上无限叠加。
  • 启发：“提示词”不仅是你输入的，甚至代码库本身也是“提示词”。

代码少，不代表信息少

  • 成熟仓库用命名、分层、错误处理和测试，把巨大的设计空间压成“照着邻居补全”；greenfield 里每个选择都悬空，信息熵反而更高。
  • 模型只会追求局部一致性，并不知道眼前的是 best practice 还是历史事故。第一桶 slop 一旦成为多数派，后面的 slop 会像复利一样增长。

Slide 29“放一个好项目给 AI 看”靠谱吗？

调研结论：猜测成立一半

  • 我的猜测：在代码库里放一个相近领域、优雅成熟的高质量系统，先让 AI 读一下，再实现需求，能得到质量更高的软件。
  • 机制上合理，但“相近、精选、按需取用”比“整个仓库塞进去”重要。
  • RepoCoder 中，迭代检索仓库相关片段比只看当前文件的 baseline 提升超过 10%；这支持“好示例有用”，却没有证明外来大仓库必然有益。
  • CodeRAG-Bench 的结论更克制：高质量 context 会帮忙，但“找对片段”和“真的用好片段”仍是瓶颈。
  • 整库输入还可能带来 negative transfer：技术栈、约束、依赖或架构哲学不匹配；它也会消耗 context，让真正相关的约束被淹没。

一个能做的对照实验

  • 固定任务、模型、token budget 和随机种子，对比：无示例 / 完整参考仓库 / 3–5 个精选 golden paths。
  • 除了通过率，还要盲测架构违规、修改扩散面、review 时间、后续缺陷和代码克隆率。我的预测：精选的端到端竖切片最稳。

Slide 30没有“超能力 AI”

你仍然需要“有概念”

对你要实现的东西有概念，现在仍然非常重要。Sadly，这只能通过学习获得。会用一学期来解释如何用软件工程的方法：给出正确指令、监控 AI 运行、防止 AI 失控……

  • 对 CS 学生来说，学科知识体系仍然非常重要：处理器、操作系统、编译器、数据库里有很多设计智慧。
  • 你需要把模型引导到你认为合适的位置上。
  • 但你不理解的东西是不能驾驭的。

学习的目标变了

  • 领域知识不是为了和 AI 比每分钟写多少行，而是给出不变量、接口边界和失败模式：什么时候“能跑”仍然是错的。
  • Bainbridge 在 1983 年就指出“自动化的反讽”：容易的部分被自动化，人留下的恰好是异常、接管和无法预演的情况，因此反而需要更深的系统模型。(Ironies of Automation)

Slide 31Research Failure：Token 花完了，知识没有增加

符号执行引擎优化

试图优化一个符号执行引擎：有一个原始 idea，问题带一点 active、open-ended research 的味道，但也只是希望往前推进一点点。

  • PhD student：GPT-5.6 Sol Ultra 启动！benchmark 丢进去，想法丢进去，花了很多 token，没有结果。

问题可能出在哪？

  • 缺的不是 token，而是便宜、局部、可归因的反馈。一个总 benchmark 分数几乎不给下一步方向。
  • “没变快”可能来自 path explosion、solver、缓存、内存、搜索策略、实现 bug 或环境噪声；Agent 不知道该强化哪一步。
  • 更要命的是：Agent 被训练成“把任务做完”，研究却允许最好的结论是“原始 idea 不成立”。没有可证伪假设，它可能把错误想法实现得越来越完整。
  • 经典的 KLEE 把问题拆成搜索策略、约束缓存、independent constraint sets 等机制，再分别测量。
  • 更合理的起点：先 profile 主导瓶颈，把 idea 改写成一句可证伪预测，造几十秒就有反馈的 microbenchmark，再做 baseline 和 ablation。

Slide 32少干预，反而做得更多

Latency 和 Throughput 是两回事

一般来说，我对要解决的问题了解更多，所以我干预，会完成得更快。但是我越来越少干预了：AI 走弯路也能完成，那我还不如切换到另一个任务。只要结果能满意，我更倾向于不管。

  • 人类干预优化单个任务的 latency；放手让 Agent 跑，优化的是一整天的 throughput。机器多走一点弯路，换回最稀缺的人类注意力。
  • 放手成立有两个前提：任务可以并行，失败可以便宜地恢复。否则“少干预”只是把故障推迟。

Review 什么？

  • 比如接口我 review 过了，实现是 AI slop，最后出问题了修就行 😂
  • 按“不可逆性 × 爆炸半径”分配注意力：接口、不变量、数据格式、权限和测试早看；可替换的叶子实现可以晚看。
  • 丰田的“自働化”也是这个逻辑：一个人照看多台机器，靠异常自动停机和 andon 报警，而不是盯住每一步。Agent 的对应物是 CI、预算、权限边界和 stop condition。(Toyota Production System)

Slide 33Context 越长，不等于记得越牢

Caveat

随着上下文增长，指令遵循会下降；但最后的 prompt、刚加载的 skill 通常仍能遵循，因此干活还是很好用的。

  • Context window 是容量，不是有效注意力。日志、补丁和工具输出不断进入工作集后，“还在窗口里”不等于“此刻用得上”。
  • Lost in the Middle 发现，相关信息放在长上下文中部时，模型往往不如放在开头或结尾时用得稳定；这也解释了末尾 prompt 和新加载 skill 的优势。

把要求从“记忆”升级成“机制”

  • 关键要求在决策点重新落地：短 checklist、阶段性重读 spec/skill、合并前复述不变量。
  • 能编码成类型、lint、property tests、CI gate 和权限沙箱的，就别只写在 prompt 里。prompt 会被压缩，失败的测试不会假装自己通过。
  • 上下文压缩应保存“目标、约束、未决问题、证据”，而不是按时间线复述发生过什么。

Slide 34在不确定性中探索

这次不是“解题”

我就是希望模型在不确定性中探索。

  • 如果所有要求和路线都想清楚了，这就是一个相对无趣的问题：Chain-of-thought 就能解决
  • 今天“帮我考虑一下几种方案”有效，但可能不是最佳的
  • 模型被训练成了“完成任务”才有奖励，所以它会给你有限的方案；complexity gap 里，那个“更好”的可能被藏起来了

谁规定“已经想完了”？

  • “给我几种”只规定了停止条件 k，没有规定覆盖率。这正是 Herbert Simon 所说的满意化：搜到“够好”就停。
  • CoT 用算力换深度：沿一条路多走几步；并行枚举用算力换宽度：让更多轨迹进入低概率的尾部。

探索的瓶颈常常不是“想不出”，而是模型太早认定“已经够了”。

提示词与上下文工程

第一讲留下的问题是：Agent 已经能做很多事，我们怎样才能驾驭它？这一讲从最常见的交互方式——自然语言指令——出发，讨论怎样让模型理解目标、遵循要求，以及在没有确定答案时继续探索。

不过，先处理一下第一讲留下的意外。“没有 token 的 CS 学生应该立即退学”上了热搜，也引来了朋友们的问询。当然不会真的让同学们退学。课堂上这句话要推动的是立即实践：不要把等待完美工具、等待别人给出评价，变成一直不开始的理由。离开现场，截图只剩下一句狠话，这本身也提醒我们，同样的文字放进不同上下文，会被理解成很不一样的意思。

模型看到的，远不止你刚输入的一句话

我们习惯把给模型的输入叫作 prompt，中文称“提示词”。从语言模型续写文本的角度看，前面的文字既是开头，也是控制后续生成的条件。进入聊天界面以后，用户更容易把 prompt 理解成对话框里的一条要求。

但对 Agent 来说，指令分散在很多地方。运行 Agent 的外围系统，也就是 harness，会提供系统指令与工具说明；仓库里的 AGENTS.md 可能约定项目规则；加载的 skill 会给出特定任务的方法；用户会不断补充目标。与此同时，代码、文件、历史消息和工具返回也会进入上下文。

第一讲里的 Pr[token | context]，其中的 context 就包含这些内容。模型下一步做什么，受到整份上下文影响，而不是只由最后一句话决定。这里还要区分指令和材料：工具返回的一段文章可能是分析对象，并不因此拥有给 Agent 下命令的资格。来源、作用范围和优先级，也属于我们组织上下文时需要考虑的事情。

所以，“提示词工程”逐渐扩展成了“上下文工程”：关心模型在做决定时能看到什么，哪些是目标，哪些是约束，哪些是证据，哪些只是过时的过程记录。写好一句话当然有用，但把相关文件、已有实现和验证结果放到合适的位置，往往同样重要。

课堂提出了一个可以立即做的小实验：让 Agent 按照需要遵循的指令类型，说明当前任务有哪些目标、工具规则、项目约定和输出要求。这个实验可以帮助我们理解它正在怎样组织任务，但模型的自述不能当作实现机制的完整说明。想知道某个行为为什么发生，还需要检查可以访问的配置、代码和实际操作结果。

例如，为什么有些命令执行前会询问用户，有些不会？不能只从“模型觉得安全吗”来解释。Agent 提出动作，外围程序还可能检查权限和审批规则，操作系统则执行实际的访问限制。提示词中的要求与程序中的机制一起决定行为；一句“请遵守规则”，并不等于已经实现了一个可靠的执行边界。

AI 降低了开始学习的成本

上下文工程听起来像开发者才需要关心的技术，但学生每天都能用到。微积分里有一步推导不想验算，数字电路有一条数据通路没看懂，计算机系统基础里始终没搞清链接发生了什么——过去，这些问题很容易被暂时搁置，一搁置就是整个学期。

现在可以立即把具体问题交给 Agent：给出一个最小例子，逐步推导，运行一段程序，再根据结果追问。课堂把这种能力称作“拖延症的克星”。过去的自我驱动，常常意味着对挫折有很高的容忍度，愿意花很久寻找一个解释；现在，我们可以把同样的精力投入到更快的尝试与反馈中。

但学习仍然需要自己的活动。一个可行的循环是：先借助 AI 弄清一个问题，然后合上资料，用自己的话重述；让它追问含糊之处，找出反例，再用推导、原文或程序结果核对，最后重新解释一遍。复述时卡住的地方，往往比读答案时觉得顺畅的地方更能暴露知识缺口。

这可以理解为让 AI 做一个随时在场的听众。它帮助你开始，也帮助你发现哪里还没讲明白。真正推动理解的，是这个循环里不断变得具体的问题和不断接受检验的解释。

写清楚“完成”是什么

模型具有很强的指令遵循能力，但首先要有值得遵循的指令。上下文中的要求越明确、越容易验证，模型就越有机会判断自己距离目标还差什么。不明确的要求，则可能让它很早就认为已经完成。

“一句话生成极品飞车”可以产生很漂亮的演示。但你心里想的，可能是有真实地图、特定美术资产、某种驾驶手感的赛车游戏。模型交出的，也许只是一个能移动、会碰撞、有速度感的网页。它未必在任何一步明显违背了指令，却在一连串默认选择之后，做出了另外一个产品。

这就是第一讲的 Intent、Spec 和 Impl 之间的缺口。镜头怎么跟随，车怎样转向，地图从哪里来，撞车以后发生什么，每个省略都留下了选择空间。模型可以把这些选择做得相互一致，但“一致”不意味着“正好是你想的”。

个人主页是另一个例子。“根据我的公开信息，制作一个现代风格的主页”，看似清楚，其实“现代”并没有排除多少可能。模板、渐变、卡片和装饰都能被解释为现代风格。如果你在意的是特定字体、颜色、留白、信息顺序和排版，就应当给出这些具体要求或参考。几个形容词，通常不能代替设计。

课堂的经验法则是：写清楚你的指令，承担一切“不明确”的后果。 它要求我们意识到，没有说明的地方，实际上是把决定权交给了模型。并不需要把所有细枝末节都提前决定，但要知道哪些地方允许它自行发挥，哪些地方决定了产品是不是你要的。

一个实用的检查办法是：让另一个人只看要求和最终产物，能否判断任务已经完成？“做得专业一点”很难判定；“页面首先展示研究方向和近期工作，手机上无需横向滚动，所有项目入口都能打开”，就提供了可以检查的行为。不能完全机械判断的品味，也可以通过示例、对比和反馈逐步说明。

完成的语义还包括失败。如果关键条件无法验证，合理的结果应当是报告哪里没完成、缺少什么证据，而不是交出一段肯定的总结。只有把这些状态说清楚，Agent 才能更可靠地决定继续尝试，还是需要新的信息。

一步有限，为什么还能完成复杂任务

一个疑问随之而来：如果模型只是反复计算下一个 token 的概率，它怎样同时满足很多约束？

一次模型前向计算的结构和深度是有限的。它不会在这一瞬间任意增加计算步骤。但模型可以把中间结果写进上下文，再利用这些结果继续生成。遇到不确定的地方，可以先尝试一种分解，检查后发现不合适，再修改。这就是课堂用来理解思维链的直觉：把一串输出看成能够存放中间状态的工作纸。

这样，更多 token 就可能换来更多计算深度。它是否有效，取决于模型有没有找到能推进问题的步骤，以及能不能识别错误。课堂借“找解常常比验解难”说明这种方法的吸引力；这是一种理解搜索过程的类比，不是在证明某个复杂性理论结论。

为了把指令遵循的难度具体摆出来，课堂给了几道故意刁难人的写作题。第一道要求写八句中文诗：句首依次是“计算机学院真牛逼”，讲一个与动物相关的故事，“二零二六九月一日”八个字还要依次出现在八句中，并且押韵。生成素材给出了这样的尝试：

计成二兔越山冈
算到零时雪满塘
机警狐衔二袋粮
学随六雁辨风向
院中九犬忽声扬
真到月明逢恶狼
牛守一夜迎晨光
逼得日升狼遁荒

检查时，可以先竖读句首，再逐句寻找指定字，最后看句尾和故事。藏头与嵌字都能对上，句尾也有相近的韵感，但“方向”的“向”与其他句尾在普通话拼音中并不完全相同，读起来有些句子也明显是为了凑约束。它展示的是模型能够寻找并修补一个多约束解，而不是宣告模型已经写出好诗。

第二道题要求一句话有十八个汉字，全部带相同偏旁，还要有意义和故事性。素材中的例子是：

洪涝淹没江港渔浦，油污漂浮，沈涛泅渡济溺。

去掉标点，可以数出十八个字，都带三点水；把“沈涛”读作人名，故事就是洪灾与油污中有人游过去救助溺水者。这里的检查比较直接，但“都含三点水”和“词典中都归为同一部首”仍然是不同要求。要交给程序验收，就得先决定检查的是哪一个。

第三道题要求所有字都同音，写一段有现代背景的文言故事，不能照搬已有的同音文。素材尝试用不同声调的 yi 音字，写一个翻译器误译、送修、恢复正常的故事。这立即暴露出另一项规格选择：“同音”是否要求声调也相同？作者靠字形区分意思，读者看文字还能猜出情节，念出来却可能几乎无法理解。

这三道题把两类评价放在了一起。藏头、字数、指定字和读音可以逐项检查；通顺、趣味和文学性则需要更丰富的判断。模型通过形式检查，说明它能够搜索和纠错，但形式检查没有覆盖的质量，并不会自动出现。软件测试也有类似的边界。

上下文中的规则，也会争夺注意力

把要求写进上下文，可以让模型在生成过程中反复利用它。项目约定使用中文，或者提交信息不添加某种署名，模型就有机会在相关时刻纠正自己的输出。不过，“在上下文里”并不保证“每次都会正确遵循”。

提示词还会带来副作用。你说“白色背景，不要半透明效果”，模型可能把这句话变成代码里的注释：“白色背景（不要半透明效果）”。它完成了背景设置，却也把原本只用于沟通的要求带进了产物。

于是，一个看似合理的修补办法出现了：再加一条永久规则，禁止把用户要求写进注释。但每遇到一次问题就增加一条规则，上下文会越来越长，约束之间也越来越难协调。这不是免费的增强。

更合适的做法，是区分长期适用的简短规则与当前任务需要的细节。项目层面留下真正稳定的约定；特定任务的方法按需加载；能够直接检查的要求，则尽量落到代码和验证结果上。白色背景可以由具体样式和渲染结果确认，不必依靠越来越长的自然语言劝诫。

上下文工程因此也包含取舍：删去一段无关说明，有时和增加一条关键要求同样有效。模型需要的不是尽可能多的文字，而是此刻做决定时用得上的信息。

“你是一位审稿人”，还不够

课堂接着把任务换成论文审稿：假装自己是 ICSE 的审稿人，阅读指定论文，写一份约一千英文词的 review，并判断是否应该接收。

模型很容易写出一份看起来像审稿意见的文本：总结贡献，列出优点和不足，再给出一个建议。问题是，它究竟完成了多少判断？“扮演审稿人”可以提示语气和输出结构，却没有把一个好审稿人的方法自动交给它。

论文的信息密度非常高。作者不仅给出了答案，也替读者选好了问题、术语、比较对象和衡量标准。如果顺着文章走完一遍才开始评价，很容易在不知不觉中接受了作者的整个框架。你以为自己在批判性思考，其实只是在作者划好的场地里打转。

可以把审稿工作拆成三条不同的路线。第一条从判据出发，先还原论文声称的贡献，再问每项贡献需要达到什么标准，证据在哪里。第二条审查证据，把核心主张、实验支持、未验证假设和替代解释一项项对应起来。第三条站到复现者或反方的位置，重算一个关键结果，寻找最小反例，明确什么观察会推翻结论。

这几条路线的价值来自问题不同。若一开始就共享同一个总体印象，最后可能只得到同一个判断的三份润色。独立形成初步意见，再比较分歧，才更容易发现原先没有看到的东西。

这也说明人的方法论如何影响 AI 的结果。你不必替它读完每一行，但需要知道什么算有根据的判断、哪些证据缺失值得追问。短程任务里，把方向带对、把标准说清楚，往往已经能显著改变产物。

当一套做法多次有效，就可以把它沉淀成 skill。Skill 看起来是一段提示词，真正值得保存的，是成功经验中的搜索策略、判断标准和检查点。它帮助 Agent 复用一种做事的方法，而不是每次重新凭第一印象发挥。

Skill 也不是越长越好。如果把所有想得到的要求都塞进去，它本身就会变成一道复杂的指令遵循题，和前面的藏头诗颇有相似之处。保留真正影响决策的内容，把机械工作交给脚本，把需要时才看的材料单独放置，才能让经验更容易复用。

为什么大仓库有时比空项目更容易

课堂提出了一个有趣的观察：从零做一个看起来不难的产品，AI 可能在某个时间点开始不断翻车；进入一个成熟的大型系统，反而能够完成相当复杂的修改。

可以从上下文的角度理解这种差别。成熟代码库已经做出了许多决定：怎样命名，模块如何分层，错误怎样传播，测试放在哪里。Agent 在解决局部问题时，可以学习附近的例子，沿着现有结构补充实现。代码量虽然大，当前任务需要自由选择的事情却可能更少。

空项目恰好相反。没有已有结构约束选择，每次局部实现都可能顺手做出一个长期设计决定。如果最初就形成了混乱的惯例，后续生成又以这些惯例为上下文，AI slop 就会不断叠加。代码库本身也是提示词。 它会示范怎样做，也可能示范怎样把问题继续藏起来。

这里不能推出“大仓库一定好改”，或者“模型会自动认出最佳实践”。它也可能模仿历史包袱。课堂进一步提出了一个未经实验验证的猜测：给 Agent 看一个相近领域、设计优雅的成熟系统，再让它实现自己的需求，能否提高质量？

这个猜测值得做实验，但还不是结论。相近领域到底有多相近？应该读整个项目，还是几个关键例子？如果参考项目的约束与当前任务不同，会不会把不合适的架构也学过来？一种比较方式是给同一任务设置无参考、完整参考和精选参考三种条件，比较实现后的修改代价与缺陷，而不仅仅看第一版能否运行。

这又把问题带回了学习。处理器、操作系统、编译器和数据库里有很多设计智慧。理解接口、不变量、状态和失败模式，才能知道该把模型引向哪里。对所做的东西“有概念”，仍然是驾驭它的前提。只是现在，学到一个原理以后，可以更快地把它用到真正的系统里。

Token 花完了，研究为什么还没有推进

能够执行长程编程任务，意味着模型在遇到错误后仍能继续：修改、构建、测试、观察，再修复。这样的闭环依赖反馈。测试失败提供了具体方向，编译器报错指出了局部问题，模型可以据此不断尝试。

但把任务交给更强的模型、投入更多 token，并不保证任何长程问题都会收敛。课堂讲了一个研究失败案例：希望优化一个符号执行引擎，已经有一个初步想法，于是把想法和 benchmark 一起交给 Agent，花了很多 token，最终没有得到结果。

原稿没有给出已经查明的失败原因，因此这里能做的是提出待检验的解释。一个可能的问题，是总 benchmark 分数提供的反馈太粗。没有变快，究竟是主要时间花在求解器里，路径搜索策略有问题，缓存没有起作用，还是修改引入了新的开销？如果这些因素混在一起，下一步应该试什么就很难判断。

另一个可能的问题，是任务把“把这个想法实现好”当成了目标，但研究真正需要回答的，可能是“这个想法是否成立”。如果原始假设就不对，继续完善实现也不会带来期待中的进展。一个能否定原想法的实验，有时比更多代码更有价值。

因此，更有用的起点可能是先测量主要瓶颈，把想法写成一个可以被实验推翻的预测，再构造能够快速反馈的小实验。确认局部机制确实有效以后，才把它放回完整系统，检查收益是否仍然存在。研究中的“推进”可以是缩小未知，也可以是排除一个方向；不能只把它定义成最终分数必须上涨。

人应该盯住哪些地方

既然人了解领域，随时干预是否最好？课堂给出的经验恰好有点反直觉：我知道怎样让某个任务更快完成，却越来越少干预了。

原因在于，单个任务的完成时间与一天能完成的任务总量，是两个不同目标。如果 Agent 走一点弯路最后也能完成，我可以把注意力移到另一件事上。机器多花一些时间，换回人的时间，整体产出反而增加。

这种取舍需要有边界。接口已经看过、结果可以检验、实现出了问题能够替换时，可以让 Agent 自己探索。相反，一个会扩散到许多模块的接口决定，一个昂贵或难以恢复的动作，就更值得提前关注。人的注意力应当按照决策影响和返工代价分配，而不是平均撒在每一行代码上。

长任务还会不断产生日志、补丁和工具输出。上下文能容纳这些材料，不代表模型在每个时刻都能同样有效地使用它们。课堂观察到，随着上下文增长，指令遵循可能下降，而最近的要求或刚加载的方法往往更容易被执行。具体表现取决于模型和任务，但工程上可以主动缩短关键要求到关键决定之间的距离。

例如，在阶段切换时重新确认目标、接口和未决问题；把能检查的不变量落实成测试；让错误在继续传播之前暴露。上下文压缩也要保存当前约束和证据，而不只是把过去发生的事情写成流水账。这样，人的放手才有可以依靠的反馈机制。

在不确定性中探索

到这里，我们一直在讨论怎样把任务说清楚。但许多有价值的任务，本来就没有确定路线。我们希望 AI 帮助探索，而不仅仅执行已经写好的计划。

“帮我考虑几种方案”通常有效，却可能过早结束。模型给出几个听起来合理的答案，已经满足了“几种”的数量要求；更有意思的方案，也许仍在它没有走到的方向里。此时，多沿一条思路想一会儿，与主动探索更多不同思路，是两种不同的算力使用方式。

课堂用取名字作例子：给一个蒋姓的小孩取好听、又有寄托的名字。如果直接要几个答案，模型可能给出自己偏好的高概率组合；许多家庭同时询问，又可能迎来 AI 时代的新一代“子涵”。

要扩大探索，可以先划分空间：从典故、音韵、方言、时代感等不同角度生成候选，再检查出处、谐音、书写和个人偏好。也可以让不同 Agent 独立提出候选或负责挑错，最后再汇总。关键在于它们是否看了不同方向、提出了不同问题，而不在于开了多少个看起来相同的窗口。

这里仍然离不开人的判断。“给更多名字”解决的是候选数量，“哪些名字值得留下”则需要评价标准。没有分辨率的筛选，可能只是把一个平庸答案变成一百个平庸答案。探索空间与评价方法应当一起设计。

人类社会其实一直在通过类似方式扩展自己的视野。每个人的教育背景、生活圈和经历都有限，也都带着偏向。与舍友讨论，去会议上听别人怎样提出问题，价值往往来自发现自己的默认前提。交流之后，每个人仍有自己的偏向，但它已经被新的经验改变。

课堂借“世界很大，人很小”的视角提醒我们，没有人能独自穷尽所有可能。群体的价值可以来自不同的局限相互补充。把这个思想带回 Agent：增加计算资源时，应当考虑怎样增加探索的差异，而不是只增加同一种思路的重复次数。

如果计算资源能够持续转化为探索能力和判断能力，这也带来了一个令人不安的未来问题：拥有大量算力的人或组织，会不会获得远超普通人的智力资源？课堂用“墙里面是超人，墙外面是动物世界”表达这种担忧。这是对未来可能性的追问，并非已经发生的终局。

对于正在学习的我们，可以从眼前开始改变做事方式：让模糊愿望获得可检查的表达，把有效经验沉淀成可复用的方法，在需要探索时主动扩展方向，又用证据筛选结果。提示词的价值，最终要落在这些行动如何改变任务的结果上。
